Use the tools exposed by the `computer-use` MCP server. Do not invoke a nested agent or assume Codex-only computer tools exist.

1. Look for the `computer-use` server's tools in your available tool catalog or the runtime's normal MCP tool discovery. `/mcp` is a human TUI command, not a tool you can execute. A loaded skill does not prove the backend is connected. If tools are unavailable, stop and ask the user to inspect `/mcp`; a paused server needs Resume, not reinstallation. For missing setup or permissions, explain `/computer doctor` and `/computer enable` (or their `atomcode computer` terminal equivalents). Do not install software, grant OS permissions or bypass a disabled server implicitly. The integration currently targets macOS 14 or later and a directly vision-capable model for screenshot tasks.
2. Use `list_apps` only to identify the application requested by the user. For a window/document task, call `list_windows`, select the exact target, then call `get_window_state` before any action. Keep the returned window descriptor on every action. `get_app_state` does not initialize the observation needed for window-targeted actions: do not mix that legacy app observation with a window selector. Do not inspect unrelated application contents.
3. Use element IDs from the latest observation. Coordinate actions require that window's latest screenshot and its screenshot ID. Respect the backend's pixel-to-window mapping; never invent IDs, scale coordinates blindly, or reuse a screenshot after the window changes.
4. Prefer element-targeted operations and editable-control values. After an action, obtain a new observation of that exact window. A snapshot bundled with the action response may predate an asynchronous UI update; it is not independent confirmation.
5. Distinguish display escapes from document characters. Accessibility tree strings and their JSON containers can escape line breaks more than once for display. A displayed `\n` is not proof that the document contains a backslash followed by n. Use the screenshot to check visible characters and line layout; use structured text only according to its encoding. When inserting a real line break, pass a newline in the tool argument, represented by one JSON escape: `{"value":"first line\nsecond line\n"}`. Do not double-escape it into literal backslash-n characters. Conversely, preserve literal backslashes when they are part of the user's actual text. Do not rewrite already-correct content solely because the tree shows display escapes.
6. Separate visible content, modified-state indicators, and durable saving. When saving is within the authorized task, issue the save once and then call `get_window_state` again; the save tool's immediate snapshot may still show the earlier modified flag. If needed, make at most two further read-only observations to let the UI settle. A disabled document-menu control alone proves neither success nor failure. If observations remain ambiguous, report what was observed and what is still unverified; do not claim byte-for-byte equality or durable persistence without evidence, or start a new editing method just to change a status label.
7. Honor the user's existing task authorization and AtomCode's approvals. Ask only when an action falls outside that authorization or an existing approval requires it. Keep global pointer, foreground input, focus and launch opt-in flags disabled; do not work around backend refusals with shell automation.
8. On timeout, disconnection or cancellation, stop issuing actions. Already dispatched effects may have occurred: re-observe and reconcile before retrying. Never replay an unknown-outcome send, purchase, deletion or submission. Code rewind cannot undo external GUI effects.

`atomcode computer status` reads configuration. `doctor` checks permissions without opening onboarding. `disable` changes configuration for future/reloaded sessions; it does not guarantee interruption of an already dispatched operation. The user manages macOS Accessibility and Screen Recording permissions for the backend application.
