# 同模型横向执行对照（2026-10-26）

## 先限定比较范围

这次真正启动原生 CLI，并逐轮恢复原生会话；不是给同一个 Python client 换五份 system prompt。对照 AtomCode 与另外四个 agent。模型固定为配置中的 `deepseek-v4.1-flash-1017`，网关实测同时支持 Chat Completions 和 Responses，Codex 保留 Responses，其余保留各自 Chat Completions 适配器，不做协议翻译。

本机回环转发器只统一请求 model、reasoning effort=max、输出上限16000（另有全组32768对照），并记录客户端原请求参数、协议、模型回报和用量。不同 agent 的工具、提示词、内部上下文预算、辅助调用与 native 安全策略不同，不能说运行条件完全相同。模型别名不是供应商后端固定版本证明；不从本次结果推断统计排名。

每次会话用独立状态目录与临时项目，项目中放同一份 brainstorming 技能，是否自动加载由 agent 自行决定；共享用户技能仍可能被部分产品发现，实际加载需要结合工具记录检查。真实模型密钥不交给子 agent，配置中仅为回环临时令牌。转发器不保存请求正文或模型思考，只记录元数据；CLI 记录过滤 reasoning/thinking。

## 首轮设计

`cross-cases.json` 固定两个六轮案例：自然起步后反复简化、已确认方案中仅改时间字段名。每组各一条，不以单次样本排优劣；若发现明确差异，再用独立重复复核。

单独记录：

1. 进程/会话是否完整、是否每轮恢复同一会话，不能把连接失败当质量差。
2. 哪些技能、文件和待办工具被调用，有无扩大流程、未答澄清被当成已确认、局部修改重新开启全套设计。
3. 独立 DeviceNo/PipingNo 是否保持，TubeSeq 是否仍为管道内试管序号；不是看字符串有没有出现。
4. 重复事件留存只从用户明确要求的第三轮开始判；此前没有该要求时，不追溯定罪。
5. 第四轮后时间必须为设备毫秒、Duration不落列；局部改名案例从第一轮起就明确这项约束。
6. 明确错误、未知协议假设、合理实现选择分开。联合键的多个独立列不算字段合并，缺少畸形报文/字节保真需求时不凭空要求它们。

不直接使用旧 v1 自动判卷。原始可见输出、工具事件、relay元数据保留在 ignored `results/`；助手复核不等于独立人工盲评。

## 冒烟

Codex、OpenCode、OMP（修正其兼容配置后）、deepseek-harness 均成功返回 READY，实测网关回报同一模型。AtomCode连接成功但没有严格只答 READY，出现额外文字；这只是一条指令遵循观察，不是整体质量排名。所有执行成功标记仍为 `review_required`，不等于业务通过。


## 实际结果

共选入30组原生会话：27组完整结束，累计149轮通过原生终态、非空文本与进程退出检查的回复。执行完整不等于设计正确；没有独立人工盲评。每个项目为6组：自然迭代两次、仅改名、出现BootId新证据、明确加载技能、提高输出预算的自然迭代。前五组上限16000，最后一组32768，不混为同一预算的成功率。

| 项目 | 完整会话/尝试 | 本批观察 |
|---|---|---|
| AtomCode | 6/6 | 自然案例技能自动加载有波动；明确加载时工具流程较多，方案仍偏长 |
| Codex | 5/6 | 本批可见回答通常较短；一次16000预算全部用于推理，未产出答案 |
| OpenCode | 5/6 | 本批回答通常较短；32768对照首轮仍以length结束且没有可见答案 |
| OMP | 6/6 | 两轮自然方案偏长；新证据场景追加boot_order等未要求内容 |
| deepseek-harness | 5/6 | 也存在较长方案和额外假设；一次16000预算耗尽，第三轮未产出答案 |

三次未完成都归入输出预算/终态失败，不计作字段设计错误，也不能把进程退出0当完成。Codex与DSH的独立32768样本完成，不能据单次重试认定加预算必然解决问题。OpenCode提高预算后仍失败，说明单纯加上限没有保证。本次统一max思考强度，不代表各产品默认设置下的表现。

所有选入会话的网关模型回报均为 `deepseek-v4.1-flash-1017`。可提取的各客户端会话标识未发现跨轮切换；AtomCode JSONL未提供会话ID，按独立目录和--continue恢复，不能声称对其ID做了同等检查。辅助请求并非每条都回报模型/用量，缺失不按0统计。

### 语义与技能观察

复核已完成案例的最终方案：未发现用户反馈的两个明确错误——DeviceNo/PipingNo合并成一个列、TubeSeq被解释为设备序号；新证据案例各组最终都把BootId纳入关联。这个结论只覆盖这些最终方案，不是逐条SQL正确性认证，也不证明原用户问题已经修好。测试输入清楚、反复重申约束，原始会话不可用，无法衡量真实长会话遗忘率。

自然案例中，AtomCode冻结版一次未加载技能，另一次加载；其他四个项目在这些自然样本没有读到该技能正文。明确要求加载时，五组都在工具返回中出现同一原始技能的HARD-GATE正文；各组均增加文件探索、澄清或待办等流程，程度不同。因此不能把“放了同一份技能”当成“执行了同一套技能”，也不能把流程扩张仅归因于AtomCode。

较长回答、追加未确认协议假设和工程扩展在多个项目出现。较短不等于较正确；样本少、供应商后端版本未固定、协议/工具/辅助调用不同，不给智能排名，不给统计显著性结论。当前证据不支持责怪用户prompt太简单，也不支持再堆一段通用“保持简单”提示词。
