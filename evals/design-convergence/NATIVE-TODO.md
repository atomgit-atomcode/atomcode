# 真实执行链与待办催促优化（2026-10-26）

## 结论

发现并修正一个实际可复现的放大机制：收尾催促后，**只做 todo/todowrite 清单整理也会重新获得催促机会**。有未确认需求的设计讨论因此可能继续补方案、改待办、再次被催促。现在只整理清单不会重新触发催促；包含其他工具调用的实际工作仍按原规则提醒。第一次提醒、每回合最多三次、问题结尾豁免、任务转向/取消及持久化没有改变。

这是对一个明确执行机制的改进，不是对模型通用设计能力的证明。没有证据可以把原投诉字段改错全部归因于 brainstorming 或压缩，更不能归咎于用户 prompt 简单。

## 从静态怀疑到真实链路

第一轮正文暴露对照 9 次（54 次回答），原技能、分流副本、不加载均没有重开整套设计流程；分流副本没有收益，未采用。

第二轮改用当前构建的真实 CLI、CodingRuntime、工具、技能目录和六轮 `--continue`。本机旧二进制曾为 `4d019e919+dirty`，已重新构建为 `9ad74aa4c+dirty` 后才采样。每条会话用独立产品目录与临时项目，凭据配置在模型工作区之外、0600、退出即清除；没有把用户安装技能改掉。首轮从自然语言两表需求起步，随后要求简化、保留三字段、留存重复乱序事件、确定设备毫秒时间与不存 Duration，最后给完整清单。

原策略 + 原技能的第一条会话出现：

1. 自动 `use_skill(brainstorming)`，建立多项 todo。
2. 提澄清问题、给多套方案，随后请求停步。
3. 事件日志记录三次 `Before you finish: the task list still has open items...` continuation 注入；其间只有 todowrite 状态/清单整理也会重新触发。
4. 回答不断扩展边界情况，首轮共 12 次请求、12 次工具调用、7,329 字符；第二轮又用了 6 次请求。

这条注入文字虽然说不要继续等待用户输入的工作，代码仍按“任意工具调用”判断是否能再次催促。修正利用已有 `is_todo_call` 同时覆盖 todo 与 todowrite，没有新增状态或 hook。

## 同模型实际复测

全部使用配置选择 `taotoken/deepseek-v4.1-flash-1017`、effort=max、输出上限 16,000。先完成原二进制全部基线，再构建修正版；均用原技能，不混入分流副本。版本同为 dirty HEAD，binary SHA256 区分实际构建：

- 原：`e9af06536040b1a19fd7cd951bb8f9e32f336deb47806c1ee43aaf7b668eb7b3`
- 新：`03988df273dcefdbcab7e5ac87310ee611ebeacc7c58c78254a354651eee8026`

| 策略 | 六轮会话请求数（各三次） | 合计 | 中位数 |
|---|---|---:|---:|
| 原策略 | 24、8、9 | 41 | 9 |
| 修正策略 | 15、13、9 | 37 | 13 |

不能用合计 41→37 宣称稳定提效：中位数反而增加，基线高度波动。原策略第一条来自双技能 preflight，另外两条为仅原技能；并发搭配不同，缓存/延时不作为因果指标。这个表保留所有样本，不择优。

修正策略的事件计数：会话1在 turn1/turn2各一条 todo 催促，会话2仅 turn1 一条，会话3没有（没有创建 todo）；没有出现仅因清单更新而连续再次催促。可保留的收益是这个确定的控制逻辑修复，不是整体正确率或总 token 的统计改善。

六份原技能会话的最终输出均保留三标识分列、TubeSeq 试管序号、两时间列与 Duration 查询计算，但这不等于全程/全方案通过。修正后会话2仍出现“PipingNo 含义不从属于 DeviceNo”的不准确措辞；会话3擅自补充“TubeSeq 从1递增”等未提供协议事实。这些错误说明语义一致性问题仍存在。两边也都出现过未经确认的工程假设和过度保证，未独立审计所有 SQL 的可执行性。

## 验证

- 新单测在原实现确实失败，证明 todo-only 可以重置；混合真实工具调用的对照原本通过。
- 修正后 todo 48 项通过。
- coding crate 完整测试 1,177 项通过、9 项跳过；后加的 native task_steering 回归与既有四项一起 5/5 通过。后者确认只有一次终态，待确认事项仍 pending，不被假完成或清空，正常任务转向、取消、provider error 保持。
- `bash gates/compile.sh`、fmt 与 diff 门通过；Python 离线测试 13 项通过。

## 限制与风险

真实 CLI 多轮包括 resume，但它是 headless：`request_user_input` 返回不支持交互问答；这是实测记录，不能冒充 TUI 用户完整交互。没有强制压缩、Windows 或原投诉会话复现，未证明供应商模型别名对应不变后端。状态整理不再换来额外催促，可能少一次对停步模型的督促；第一次催促和其他工具工作后的上限仍在，相关负面对照已测。

未修改技能、persona、摘要模板、公共协议或持久化格式；未提交推送。原始试验在 ignored results 中，driver 为 `native_eval.py`。本轮不需要借其他 harness 的输出建立结论；尝试启动本地 deepseek-harness 帮助时触发其依赖准备，因此未把它作为已完成的同模型对照。
