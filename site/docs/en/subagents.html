Subagents

When a task splits cleanly — parallel edits, mechanical repetition, or read-only investigation — the main agent can hand subtasks to short-lived subagents through the task tool. Each subagent runs in its own isolated context; the main agent keeps the cross-file reasoning and owns the final result. The task tool is on by default.

Two kinds of subagent

TypeWhat it can do
exploreRead-only investigation — reads and searches the codebase to answer a “where / how” question, then returns findings. Cannot edit files.
workerExecutes a tightly-specified change. Reads freely, but its writes are confined to a declared scope.

How they run

  • Subagents run in parallel, up to max_concurrent at a time, each in an isolated context.
  • The native task accepts a model selection ID on each call. When omitted, it uses the current session's model. Only models available for delegation in this session can be named.
  • The main agent reviews each result before continuing — a subagent proposes, the main agent decides.

Worker scope & safety

A worker subtask must declare a scope: a list of working-directory-relative globs it is allowed to write, e.g. ["src/auth/**", "Cargo.toml"]. This is enforced, not advisory:

  • Writes outside the scope (edit_file, write_file, search_replace) are hard-denied — not prompted — by the WorkerScopeGate.
  • Available tools depend on the runtime configuration. Team members have no general-purpose shell.
  • A dispatch that contains any worker is treated as a Risky action, so it goes through approval first, with the scopes shown.
  • When several workers run at once, give them non-overlapping scopes so they cannot clobber each other.

Configuration

Tune the subagent pool in ~/.atomcode/config.toml:

[subagent]
max_concurrent = 3     # parallel subagents at once (min 1)
max_rounds     = 0     # per-subtask model-round cap (0 = unbounded)

Child rounds are unlimited by default; existing explicit positive budgets are preserved. Set [subagent] max_rounds = 0 or ATOMCODE_SUBAGENT_MAX_ROUNDS=0 to remove an old 200-round limit. Positive budgets allow at most one extra text-only closing request. Concurrency, cancellation and repetition guards remain independent. External Codex/Claude agents retain their own execution policies.

KeyDefaultMeaning
max_concurrent3How many subagents run in parallel
max_rounds0Model-round high-water mark per subtask; 0 = unbounded

Environment overrides: ATOMCODE_SUBAGENT_MAX_ROUNDS take precedence over the config values.

Custom team roles

The team (team) picks members by role. Besides the built-in roles you can define your own as Markdown files in either of:

  • <project>/.atomcode/agents/<role>.md — this project only;
  • ~/.atomcode/agents/<role>.md — every project.

The file name (without .md) is the role's name. A file named like a built-in role replaces it; when both directories have a file of the same name, the one in your home directory wins.

A role file is a header of fields between --- lines, then the role's instructions:

---
permission: explore      # required: explore (looks, changes nothing) | worker (may edit files within its assigned scope)
difficulty: hard         # required: simple (the fast model) | hard (the strong one)
effort: high             # optional: low | medium | high | xhigh | max
model: glm-4.6           # optional: a model selection id, overriding difficulty
when: designing systems  # optional: one line on when to hand it work
tools: read_file, grep   # optional: limit its tools, chosen from what permission allows
---
You design. Read the existing code first, then propose a design and its trade-offs.
FieldRequiredValues
permissionyesexplore (read-only investigation) or worker (scoped writes)
difficultyyessimple (fast model) or hard (strong model)
effortnolow / medium / high / xhigh / max
modelnoinherit uses the parent model, auto chooses by difficulty from eligible ranked models, or supply a model selection ID. Omission keeps legacy difficulty routing.
whennoOne line on when to hand this role work
toolsnoComma-separated tool names, selected from permitted built-ins and read-only MCP queries granted to this role
allowed_toolsnoInline array alias for tools. Omit for role defaults, or use [] to clear this list.
denied_toolsnoInline array of tool names to remove, even if also allowed.
allowed_mcp_serversnoInline array of servers. Only previously granted read-only queries are eligible. Omit to keep the existing per-tool behavior, or use [] to disable MCP for the role.

Use a build that supports these fields when sharing role files. Older builds ignore the new tool-list fields. For a role shared with older builds, keep using the tools: allowlist they understand.

Two things to note:

  • This permission is not the CLI's --permission-mode (plan / accept_edits / auto); they only share a name. This one decides whether the member may change anything; that one is how the whole session asks for approval.
  • This is not Claude Code's agent file format. name, description and user_invocable are not read: the role's name is the file name, and its tools are limited with tools.

A role file that does not parse is skipped and the session starts anyway. You are told once per session which file was skipped and everything that is missing or wrong in it; a file named like a built-in role leaves the built-in in use.

Query skill documentation from a Team member

In the user-level mcp.json, add a per-role grant to the documentation server. For example, on the docs server, grant the research role one tool:

"teamReadOnlyTools": {"research": ["search_docs"]}

Set tools: read_file, mcp__docs__search_docs in research.md. The server must be connected and advertise readOnlyHint for that tool. User-level grants apply across projects by role name. Grant only trusted read-only implementations. Project MCP configurations cannot issue these grants. Members receive tell_parent automatically.

Each query leaves a reference in the lead session without waking the lead. The lead can use team(action="evidence", name="member", reference="reference") to inspect the original arguments, returned text and error status, including after resuming in the same project.

For a Python-only skill, the repository example examples/mcp/skill_docs.py exposes a fixed lookup script over stdio MCP. Install the adapter and trusted skill in a user-controlled location. Configure the server command as uv with arguments run, --script, the absolute adapter path and the absolute path to the installed scripts/search_docs.py. Append --query-option=--query if the script requires a named query argument. The example passes one search string and expects UTF-8 text.

Turning it off

The task tool is enabled by default. To remove it entirely, set:

ATOMCODE_SUBAGENT=0 atomcode

Any of 0, false, or off disables it; unset (or any other value) leaves it on.
