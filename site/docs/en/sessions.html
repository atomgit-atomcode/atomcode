Sessions & Undo

AtomCode persists every conversation by default, so you can restore, resume, clear, or compact at any time. A single /undo rewinds conversation memory back to any earlier turn.

Session lifecycle

Each atomcode launch creates a session. A session contains:

  • Full message history (user prompts, AI replies, tool calls)
  • The associated working directory
  • The associated provider / model
  • Token usage stats
  • File-history snapshots of every file edit made in that session

Session data is persisted under ~/.atomcode/sessions/, grouped by project (working-directory hash).

Are the system prompt and original task retained?

Distinguish the system prompt, assembled by AtomCode from its persona, project instructions and capability guidance, from your first task message, which is your own input.

ContentDuring normal conversation and compaction
The currently active system promptContinues to be used in subsequent model requests. Ordinary history summarization does not discard it.
The text of the first real user messageIs protected from compaction. Normal compaction does not delete the original task or replace it with a summary.
Later messages and tool resultsMay be summarized or shortened. Saving session records to disk does not mean every request sends their entire original text.

This describes normal context compaction. Explicitly running /clear, starting a new session with /session, or rolling back the conversation with /undo / /rewind changes the effective history. Images and other attachments may also be converted or folded separately; protecting message text does not mean attachments are always sent unchanged.

Is the system prompt identical after resuming?

/resume and --continue restore effective history from persisted session records, including the original task when it is still part of that history. Saved session context also participates in restoration. The system prompt is assembled from the currently loaded components; version, configuration or project-instruction changes can make it differ from the prompt at session creation. Resuming is not a byte-for-byte replay of the original model request.

Where can I inspect the current system prompt?

In the TUI, use:

/context prompt    # Inspect the currently assembled system prompt
/context persona   # Inspect the persona and its append settings
/context           # Inspect context-budget and usage statistics

/context prompt shows the application-assembled system prompt, not a complete model request containing tool definitions and all conversation history. These prompt-text inspection commands refer to the TUI; the WebUI's /context budget statistics are not a full prompt viewer. See the command reference.

Resuming sessions

Continue the last one from the CLI

atomcode -c        # or atomcode --continue

The most common case: pick up exactly where you left off yesterday.

Switch sessions inside the TUI

/resume

Opens the session picker. It lists this project's historical sessions newest-first; jump to any of them quickly. Each entry uses the most recent user prompt as its label for easy recognition.

While a turn runs, select another session in /resume or run /resume <id>. The current session keeps running in the background; the view switches only after the target is ready. A failed open leaves the current session intact. Returning to a background session in this process reuses its runtime instead of restarting the task. Use /bg list to inspect up to 16 background slots.

Switching remains restricted while awaiting approval or interactive input, reconfiguring, or sharing live sync with the WebUI. If all slots are full, stop an unneeded session with /bg drop <N>. This applies to the TUI; it does not add running-session switching to the WebUI.

Start a clean new session

/session

Spin up a fresh context without changing the working directory. Good for "the previous task is wrapped — onto something totally unrelated".

Background sessions (/background · /bg)

Need to juggle multiple tasks without losing the current conversation? /background (alias /bg; the two are equivalent) parks the current session in the background and opens a fresh foreground — switch back any time. Up to 16 concurrent background slots.

CommandWhat it does
/bgSend the current session to the background and open a new foreground
/background <task> (same as /bg <task>)Start a one-shot task in a background slot without swapping foreground (see below)
/bg list (alias /bg ls)List all background sessions: slot, ID, state, created, summary
/bg <N>Resume slot N as foreground (the current foreground is swapped to background)
/bg drop <N>Drop background slot N
/bg help (aliases -h, --help)Show built-in help

Session states

The state column in /bg list reflects what each background session is doing:

  • running — the model loop is still executing; tool calls and output keep advancing in the background
  • idle — the model turn finished; waiting for your next prompt
  • done — the session was explicitly ended
  • cancelled / error — interrupted, or the background run hit an error

So /bg isn't just "suspend" — the model actually keeps working in the background; when you switch back, the result is already there.

/background <task> — one-shot dispatch

If you don't want to swap foreground/background manually and just want to "have it look something up real quick", just pass a task (both names work) — /background <task> or /bg <task>:

/background list every unused dependency under src

It starts a one-shot task in a /bg slot (configured with a read-only tool subset by default so the main conversation context isn't polluted). When done, check /bg list, use /bg <N> to read the result, /bg drop <N> to discard.

Typical pattern

The foreground is debugging module A; the model is editing and running cargo check (slow). You realise you also want to refactor module B — /bg straight to a new foreground for B. The build on A finishes in the background, state flips to done; /bg 1 to switch back and read the result.

Background lifetime and multiple processes

Background sessions depend on this AtomCode process. Exiting stops their runtimes; this is not process-independent execution. Saved conversations can be resumed, but their original tool processes are not guaranteed to keep running.

One installation is enough: run the same executable in multiple terminals with different sessions. Different sessions in the same project and home can run concurrently. An exclusive lease prevents two runtimes from writing the same session in the same storage bucket. Interactive resume may fork a session held by another process; check the notice. Config writes use a cross-process lock and atomic replacement, but settings remain shared.

Separate ATOMCODE_HOME values isolate configuration and session storage. Neither session leases nor separate homes protect project files. Use separate Git worktrees when agents edit concurrently to avoid conflicting file or Git operations.

Rewinding conversation memory with /undo

/undo rewinds conversation memory to before a given turn — removing that turn and everything after it — and drops the prompt you typed for that turn back into the input box so you can edit and resend it.

/undo      # rewind the last turn
/undo N    # rewind to turn N (1-based; counts only the prompts you actually typed)

The scrollback dividers for the removed turns are cleared too, and the session is saved immediately — so your next /resume reflects the rewound state.

Where the boundary is

/undo rewinds conversation memory only — it does not restore files on disk. If the AI edited code during those turns, those changes stay in your working tree; use /diff to review and revert them manually, or rely on git. You can't /undo while a turn is in flight — press Esc to cancel it first.

Safe rollback with /rewind

/rewind lists recent user prompts and lets you choose the scope: conversation only, code only, or both conversation and code. Code rollback requires a Git worktree and is confirmed before it runs. For a simple one-turn conversation rollback, /undo remains the lighter option.

Recovery after an interrupted exit

AtomCode saves temporary progress while a turn is running. After a terminal crash or network interruption, /resume attempts to restore the last user prompt, generated response, and tool-call progress instead of falling back to the previous completed turn. Pending permissions and questions are never auto-approved.

Inspecting and managing token usage

/cost

Shows cumulative input / output tokens for the current session. When the number approaches the provider's context_window:

  • Use /compact to compact history (early messages become a summary)
  • Or just /session and start fresh
  • To avoid keeping large tool-call results, tell the model in the prompt to "stop re-reading those big files"

Context summary count

TUI and WebUI show the recorded summary count beside existing token usage, hidden before the first summary. Progress appears in the running status or conversation, never in the footer; completion leaves a numbered record. Failures, cancellations, no-ops and tool-output cleanup do not increase the count.

The count comes from the session event log, so resume and reconnect do not double count it, and a new session starts fresh. Unknown history before import cannot be reconstructed; undo does not erase the historical fact that a summary happened.

Multi-project workflows

AtomCode groups sessions by working directory. Recommended ways to switch:

  • From the CLI, specify with -C
  • While running, use /cd; default_workdir is persisted automatically
