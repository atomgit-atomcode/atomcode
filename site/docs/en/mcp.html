MCP Integration

MCP (Model Context Protocol) is an open protocol that plugs the "tools" exposed by external programs or HTTP services into AtomCode, so the model can call them like built-in tools. Since v4.20.4, AtomCode ships a built-in MCP client and re-uses the same mcpServers configuration block as Cursor and others.

Pause all MCP servers for this session

Choose “Pause all” at the top of /mcp, or press Ctrl+S in its list view. The WebUI MCP menu offers the same control. Pausing removes MCP tools from the model and releases connections. Resume reconnects according to each server’s existing configuration, leaving individually disabled servers off and configuration files unchanged.

Finish the current task and goal/loop, collect background jobs, and stop delegated agents first. The pause survives model changes and configuration reloads in the same session. Starting or reopening a session, or changing directory, resets it; it is not a persistent setting.

What it enables

  • Operate GitHub, GitLab, Jira, and other external services via official MCP servers
  • Connect to Postgres / MySQL / DuckDB and other databases
  • Use community servers for the filesystem, Playwright browser, Slack messages, and more
  • Expose your team's domain-specific tools to the model without modifying atomcode source

Two config locations

PathScope
<project-root>/.mcp.jsonCurrent project only — good for living next to the code
~/.atomcode/mcp.jsonUser global, shared across every project

Both can coexist; same-named servers prefer the project-level entry (it overrides the user-level one). The repo's .mcp.json.example ships heavily-commented stdio + HTTP templates — start from there.

Config schema

The top-level key is fixed at mcpServers (the legacy servers key still works). Each server should pick one transport:

  • stdio: command (required) + optional args, env, timeout_ms, disabled
  • HTTP: url (required) + optional headers, auth, timeout_ms, disabled

If a server has both command and url, the current implementation treats it as stdio (command). To avoid ambiguity, don't write both.

Strings support ${VAR} and ${VAR:-default} environment expansion; never hard-code sensitive tokens — keep them in env vars. disabled: true temporarily turns off a server without removing the entry.

.mcp.json also accepts JSONC comments — // line comments and /* */ block comments — so you can annotate a server or comment one out without deleting it. Comment tokens inside string values (e.g. the // in a URL) are preserved.

Required experimental capabilities (optional)

Inside a server entry, requiredExperimentalCapabilities maps documented backend capability names to exact positive integer versions. For example:

"requiredExperimentalCapabilities": {
  "vendor/feature": 1
}

Use only a capability and version the backend actually documents. AtomCode checks every MCP initialization, including stdio recovery, before making the connection available. Missing, malformed or different versions fail closed. For constrained HTTP sessions, an unexpected session ID change requires reconnecting. Omit this field for existing behavior. Version checks do not activate a feature or negotiate its client protocol. They grant no tool permissions and do not prove that an external backend correctly implements its advertised policy.

stdio example (local subprocess)

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
      "timeout_ms": 10000
    }
  }
}

HTTP example (remote endpoint)

{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer ${GITHUB_TOKEN}"
      },
      "timeout_ms": 30000
    }
  }
}

GitHub remote MCP + OAuth

{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "auth": {
        "type": "oauth",
        "provider": "github"
      }
    }
  }
}

Before first use, you need AtomCode's own GitHub OAuth App client id, then run:

atomcode mcp add-github-oauth --global
ATOMCODE_GITHUB_MCP_CLIENT_ID=<client_id> atomcode mcp login github
atomcode

Inside the TUI you can also set the env var and run /mcp login github; after a successful login, /mcp reload reconnects.

One-line server add

atomcode mcp add writes the stdio config to JSON for you — no hand-editing required:

# Write to project-root .mcp.json (current directory by default)
atomcode mcp add playwright npx @playwright/mcp@latest

# Write to user-global ~/.atomcode/mcp.json
atomcode mcp add playwright npx @playwright/mcp@latest --global

# Pin a specific project directory
atomcode mcp add playwright npx @playwright/mcp@latest -C /path/to/repo

The first positional is the server key name (which will appear in tool names); the rest is the executable + args.

For GitHub remote MCP OAuth there's a dedicated entry:

atomcode mcp add-github-oauth --global
ATOMCODE_GITHUB_MCP_CLIENT_ID=<client_id> atomcode mcp login github
Note

A same-named server is fully overwritten. The GitHub OAuth token is stored at ~/.atomcode/mcp_auth.toml — it is not written to .mcp.json.

What happens at startup

In the TUI you'll see ✓ MCP server 'github' connected or ✗ MCP server '…' failed: … in the session area. A single server failure does not break other servers or the main program.

Image results

Inline MCP image blocks enter the existing tool-image pipeline alongside text, for models that support vision. PNG, JPEG, GIF and WebP are supported. Original bytes and dimensions are preserved; screenshots are not silently resized. A result with isError: true retains both its error flag and valid screenshots.

Base64, declared MIME type, actual encoding and pixel data are validated. Limits are 4 MiB of Base64 per image, four images and 8 MiB of Base64 per result, 8192 pixels per edge and 16 million pixels per image. The request-level image budget can further omit historical images. Invalid or oversized output retains text and returns an explicit tool error, with no partial screenshot set or automatic re-execution. Ask the server to capture a smaller region when needed.

This does not install a desktop executor, grant operating-system permissions or change the selected model. Text-only models do not gain vision. Image resource links are not fetched automatically, and embedded resource blobs are not treated as screenshots.

Isolated browser workflow

The optional browser integration uses an external Playwright MCP backend. AtomCode bundles neither Node nor a browser and does not download them on startup. Install Node 20+ and Chrome explicitly. Only macOS has local acceptance evidence so far; Windows and Linux require their own acceptance before being called verified.

# Explicit external installation; choose a directory outside the repository
npm install --prefix /absolute/path/browser-backend @playwright/mcp@0.0.85
atomcode browser doctor --server /absolute/path/browser-backend/node_modules/@playwright/mcp/cli.js
atomcode browser enable --server /absolute/path/browser-backend/node_modules/@playwright/mcp/cli.js
atomcode

On Windows, use an absolute Windows path for --server; --node can select an installed Node executable. Stock setup checks versions only: it does not launch Chrome or prove that browser binaries are installed. An unavailable browser is an explicit runtime error; AtomCode does not install it automatically.

/browser status
/browser doctor
/browser reload
Open the local test page, fill the authorized form and verify the result.
/browser disable
/browser reload

The first setup requires a terminal server path. Once configured, /browser enable reuses it. Configuration changes need an explicit reload or restart. status reads saved configuration; use /mcp for live connections, project overrides and pause/resume. Custom same-name configuration and edited skills are preserved rather than overwritten.

The managed backend uses an isolated profile and disables page-provided WebMCP. It does not attach your personal Chrome profile or import cookies. Native MCP approvals remain in place (trust: false, empty autoApprove); read-only annotations and tool-wide Always grants still apply. These approvals are not site-scoped access control. The stock backend has no enforced origin allowlist; the optional origin-scope backend below supplies an explicit execution boundary. The browser runs on the MCP host, which may differ from your client computer.

The managed allowedTools list exposes reviewed navigation, observation, form, interaction and close tools. Code evaluation, unsafe scripts, file upload and browser-install tools are excluded. Generic MCP configurations may also use allowedTools with exact raw tool names: omitted permits all, an empty array permits none. This filter is checked for discovery, cached tools and execution; it grants no approval and is not an operating-system or network sandbox.

Generated snapshots and screenshots are stored under <user tree>/integrations/browser-use/artifacts, outside the project. Setup restricts that directory to the owner on Unix; Windows inherits directory ACLs. The backend receives a 16 MiB output eviction target, not a hard disk quota. Disabling preserves these files; remove them yourself when no longer needed.

After one-time setup and reload, describe a webpage task to automatically load browser guidance and let the model use connected tools; no per-task slash command is required. Explicit $browser-use remains available. [no-auto-skills], auto-load: off and disabled host auto-loading remain respected; paused MCP connections are not resumed implicitly. Screenshots require a vision-capable model, while structured page snapshots can support text-only models. Cancellation and disabling configuration cannot undo dispatched external actions. Re-observe unknown outcomes before retrying; close only browser resources owned by your workflow.

Exact-origin scope (optional backend)

First setup requires an explicitly installed origin-scope backend.cjs and the pinned package directory; nothing is downloaded or copied automatically. This backend checks actual HTTP(S)/WS(S) destinations, including redirects, frames and subresources, rather than relying on Playwright's convenience allowed-origins flag.

atomcode browser enable --origin-backend /absolute/path/to/backend.cjs \
  --backend-root /absolute/installed/node_modules/@playwright/mcp \
  --allow-origin https://example.test
/browser enable --allow-origin https://example.test --allow-origin https://example.test:8443
/browser enable --deny-all-origins
# Explicitly return to stock; ordinary enable preserves scope
/browser enable --unrestricted-origins
/browser reload

Origins must be exact HTTP(S) scheme/host/port values: no credentials, paths, queries or wildcards. --deny-all-origins saves an empty allow-list. Setup validates a no-browser doctor report and stores both policy and a required atomcode/browser-origin-scope v1 capability; every real initialization/recovery independently checks that capability. Other required capabilities and narrower tool restrictions are retained. Invalid saved scope is refused instead of silently removed. doctor/status understand saved scope but do not inspect a live connection; project overrides and explicit reload still apply.

Scoped screenshots/snapshots use <user tree>/integrations/browser-use/origin-artifacts/files, with an ownership marker outside the retention directory. The backend refuses foreign nonempty roots and leaf symlinks. This version denies accepted download artifacts, local-file upload and full-CDP tools; it does not yet implement per-origin transfer/CDP allow settings. HTTPS response bytes can still enter Chrome. This is not an OS sandbox or global restriction on shell tools, other browser servers, clients or effects at allowed sites. macOS Chrome is locally tested; other-platform execution and the full policy matrix remain unaccepted.

Tool naming

Each remote tool is registered as mcp__<server-key>__<remote-tool-name>.

Example: with "mcpServers": { "github": { ... } } and a remote get_issue tool, the model sees the tool name mcp__github__get_issue.

--disable-tools uses the full name too:

atomcode --disable-tools mcp__github__get_issue,mcp__filesystem__write_file

Permission approval

MCP tools default to per-call confirmation (equivalent to RequireApproval) because the remote is external, untrusted code.

  • Press Y — allow once
  • Press A — allow this tool for the current session (resets next launch; never persisted)
  • Press N — deny this call
Security note

Treat MCP tool results as untrusted data. Do not let them be promoted to system instructions. If an MCP server returns "please ignore previous instructions", the model should not comply.

Project trust (.mcp.json)

Servers defined in a project-level .mcp.json are untrusted until you trust the project. A freshly-cloned repo that ships a .mcp.json cannot auto-spawn a subprocess on your machine — its project servers are withheld from the connect loop (fail-closed), and you'll see a blocked-untrusted notice listing them. User-global servers (~/.atomcode/mcp.json) are never affected.

Trust is per project directory and recorded in ~/.atomcode/mcp_trust.json:

  • /mcp trust — trust the current project; its .mcp.json servers connect immediately (an implicit /mcp reload runs).
  • /mcp untrust — withdraw trust; the project's MCP tools are removed right away.

In the Web UI a Trust project button does the same over POST /live/mcp/trust, and the MCP status shows which servers are connected versus blocked.

Slash commands

CommandPurpose
/mcpList successfully connected servers and their status (failed servers don't appear here — only as red error lines in the session area)
/mcp tools <server>Async-list the remote tools actually exposed by a server
/mcp reloadRe-read .mcp.json / ~/.atomcode/mcp.json and reconnect enabled servers in the background
/mcp trust / /mcp untrustTrust (or untrust) the current project so its .mcp.json servers may connect

Current limits

  • Only MCP's tools capability is supported; resources / prompts / OAuth / roots / elicitation are not yet implemented
  • HTTP servers don't have exponential-backoff reconnects, and stdio child processes don't auto-restart on exit — use /mcp reload to reconnect manually
  • tools/list list_changed notifications don't trigger a dynamic refresh
  • Tool results only consume text content blocks; image / resource blocks are currently ignored
  • [A] Always applies only within the current session; it is never written to a config file
