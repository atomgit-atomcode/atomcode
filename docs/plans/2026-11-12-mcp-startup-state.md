# MCP startup state in the first request

Baseline `release/v5.2.7`, `32a774d6fed2c5f909121676ffda32f5f79333b7`, clean worktree. The actual ACP pending-EOF diagnostic exposed a first prompt without browser schemas while its configured backend was still starting. Inspected current producers/consumers, publication/readiness, withdrawal, runtime wait handling, ACP prompt/cancel, headless CLI/daemon waits and recent history.

ADR 0002 explicitly keeps interactive session transitions nonblocking. `wait_mcp_ready` is a bounded caller policy for headless surfaces; adding an ACP pre-submit wait would change interactive behavior and needs to preserve cancellation before submit. This change therefore does not introduce a wait, another connection owner, request queue or lifecycle hook. CodingRuntime continues to own the registry; its `mcp-host` row owns the model-facing catalog and startup explanation.

While initial reconciliation is pending and configured clients are connecting/connected, that row contributes a short trusted startup-status fragment before the first model request. It explains that absent schemas do not prove missing configuration and forbids guessing calls or bypassing permissions. It contains no server names, credentials, errors or backend-provided instructions. It remains separate from the untrusted server-instructions fragment. Initial catalog completion, withdrawal and row disposal remove it. Existing generation/publication ownership controls all mutations; the fragment does not live in session storage.

The regression holds a real stdio server's tools/list behind a local file gate. A genuine first runtime/provider request must have no external schema yet, but must explain pending discovery. After explicit release and existing readiness completion, the following request must offer the tool and no longer contain stale startup text. This verifies actual provider input and tool availability rather than mirroring string assembly alone. It does not guarantee model compliance or make a still-connecting tool callable, and it does not change the intentional interactive readiness policy.

The regression also exercises withdrawal while discovery is still held, without rebuilding the mounted tree (the state a failed capability reload can leave). Its following provider request must contain neither an external schema nor stale startup guidance. The baseline failed the actual-provider-input assertion (`/tmp/atomcode-mcp-startup-before.log`); the initial corrected ten-test storage suite passed (`/tmp/atomcode-mcp-startup-storage.log`) before adding this withdrawal branch.

The first full coding run (`/tmp/atomcode-mcp-startup-coding.log`) passed the new discovery/withdrawal regression but exposed an older runtime cancellation assertion incompatible with the already-delivered awaited backend retirement. Its criterion was aligned with that contract and independently passed; details are in the [controlled download runtime follow-up](2026-11-12-controlled-download-runtime-acceptance.md). Full coding regression is repeated after that actual change; it is not treated as an unexplained flaky rerun.

Final coding regression: `/tmp/atomcode-mcp-startup-coding-final.log`, 1,338 passed, eleven existing opt-in tests skipped; the new real-provider-input/withdrawal case and adjusted owned-cleanup criterion both ran. Two pre-existing restore/undo tests take about 65/71 seconds; neither failed. Formatting, layer and product-directory gates passed. Workspace compile gate passed (`/tmp/atomcode-mcp-startup-compile.log`), including all targets, feature targets and both negative controls. Cargo.lock is unchanged with all three forbidden package counts zero. No dependency, version, persistence, grant, driver wait or runtime-owner changes.
