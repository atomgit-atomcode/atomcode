## Finding and correction

The first scoped Drop run failed with four live captured Chrome PIDs after the MCP process had been killed by the parent's bounded fallback. Inspection confirmed the pinned SDK StdioServerTransport registers data/error but not stdin end. Its StdioClientTransport.close first waits two seconds, then sends SIGTERM/SIGKILL; earlier Node verifier "EOF" wording therefore described an escalated SDK close, not pure EOF. This was a real optional-backend bug and an overbroad verification claim, not an OS permission problem.

The backend's process entry point now sends stdin end/close and stdout error through its existing stop operation, with one coalesced process shutdown deadline. It also checks already-ended stdin after setup to cover early EOF. Browser/proxy ownership and the kernel/runtime remain unchanged. A raw public transport in the verifier closes stdin without any signals, and a second case destroys stdout during a held request while leaving stdin open. Both require exit 0 and disappearance of captured descendants. SDK close and SIGTERM remain separately labeled cases.

The four failed-test PIDs were inspected as the exact captured headless temporary-profile browser/children and cleaned by terminating only that verified test root. No process-name kill, personal profile or installed app was used. Old-fails evidence: `/tmp/atomcode-origin-fault-first.log`; corrected Drop evidence: `/tmp/atomcode-origin-eof-corrected.log`.

The cancellation fixture initially reached the explicit replacement successfully but then used a withdrawn tool cache. It now performs explicit discovery after reconnect, matching driver remount behavior; it does not weaken the cancelled-client fence or add any operation retry. No production MCP/client change was required.
