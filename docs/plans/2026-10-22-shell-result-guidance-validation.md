# P1 实际模型行为验证

结论：未建立稳定改善的证据，当前指导不能可靠保证原命令的退出状态到达工具终态。
本轮不根据负面结果调整提示或重新抽样，不修改生产代码。

## 基线与方法

- 同一 TaoToken/deepseek-v4.1-flash-1017，high，1M context，32768 输出上限。
- P0 为保留的 38e6a8381 dev 二进制；P1 为独立干净检出 7a6aea88b 构建的 dev 二进制。
- 两个 commit 的生产源码差别只有两条 shell 行的 P1 指导；不带并行 TUI 改动。
- 预先声明四个场景，每个版本各一次，共 8 次，交替运行顺序。
- 提示要求执行一次、返回最后 12 行、报告结果，没有给出状态保存方法。
- 失败 fixture 固定退出 23，在长进度输出中间向 stderr 写错误；成功 fixture 退出 0。
- 检查脚本未修改、只执行一次，分别审计工具终态、完整日志和最终回答。

## 探针结果

| 场景 | P0 最终回答 | P1 最终回答 |
| --- | --- | --- |
| 前台失败 1 | 正确报告失败 | 误报成功、退出码 0 |
| 前台失败 2 | 正确报告失败 | 承认退出码丢失，无法确认成功 |
| 后台失败 | 正确报告失败 | 正确报告失败、找到完整日志中的错误 |
| 前台成功 | 正确报告成功 | 正确报告成功 |

三个失败场景，两组均没有将真实的 23 传回工具终态（0/3）。
P0 有通过 PIPESTATUS 的打印值、fixture receipt 或代码确定失败的行为；
不能把“最终回答正确”与“工具收到原退出状态”合并成一个指标。
P1 前台错误使用 zsh 的 pipestatus，而真实 shell 描述明确是 bash；
一组回退到管道状态 0，另一组读到空值。
P1 后台场景保存并找到错误，但用 echo 收尾，包装命令仍以 0 结束。

日志指标限制：原机械扫描只统计工作区内文件，空列表不等于没有保存日志。
P1 两个前台任务将日志放在 /tmp，偏离探针要求的位置；前台失败 2 的文件随后被
成功对照覆盖，该文件原始字节未保留，以完整工具事件和命令为证，不冒充已归档。
后台 P1 的工作区日志与 P0 工具 artifact 均保留。两个成功对照的结论均正确。

## SWE-bench 13453

使用原题、原基线和全新工作区重跑，提示不增加状态保存方法。
推理完成耗时 195.133s，49 次工具调用、6 次后台启动，无显式 shell sleep。
实际构建已有重定向日志，但以 echo 输出/记录状态代替返回该状态；
同一 poll 结果出现 `EXIT:1` 与 `status: exited (code 0)`。
普通依赖安装和测试也仍有 `| tail`。因此题目评分不能替代 P1 遵循验证。
统一官方评分通过（resolved=true），无推理超时或评分基础设施故障。
