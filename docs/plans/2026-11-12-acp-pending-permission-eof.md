# ACP pending permission EOF acceptance

Baseline `release/v5.2.7`, `e9f44774c221ee60c41d8f38abe06d4f746c51f5`, clean worktree. Inspected the v1/v2 permission handlers, shared session teardown, existing native in-flight EOF test, kernel session facts and recent ACP history. CodingRuntime remains the only live runtime owner; unanswered permission requests fail closed at the existing permission boundary, and EOF drains sessions through existing Cancel/Shutdown commands.

Two deterministic acceptance cases drive production `serve_over` with raw JSON-RPC lines through the SDK's public Lines transport, not its Client/SentRequest request API. After observing one actual `session/request_permission`, they do not respond, cancel or close the session; they drop input while retaining output. A local destructive fixture operation must never start: the sentinel stays unchanged, the native log has no ToolStarted, exactly one error tool result and one turn terminal, and the native lease can be reacquired after the server returns. Both protocol versions use their actual initialize shape.

This line-level test does not alone prove subprocess stdio/resource disposal or actual model behavior. Those require separate real stdio cases. Browser or desktop GUI acceptance and other remote transport faults remain separate requirements.

Deterministic results: `/tmp/atomcode-acp-pending-regression.log`, all eighteen ACP end-to-end tests pass with no skips, including both new pending-permission EOF cases and an explicit native Cancelled assertion. The initial fixture diagnostics are preserved in `/tmp/atomcode-acp-pending-eof.log`: v2 used v1 initialize field names, and the v1 `rm -f` fixture did not reliably require destructive approval. The corrected fixture uses the v2 `info/capabilities` shape and the same recognized `rm -rf` destructive operation as the existing approval contract test, restricted to a disposable local sentinel. `/tmp/atomcode-acp-pending-eof-shaped.log` first verified both corrected cases before the full run added the stronger native cancellation check. No production code change was needed.

## Actual stdio and configured-model evidence

Fresh independent `/tmp/atomcode-acp-pending-stdio-v1-ready` and `/tmp/atomcode-acp-pending-stdio-v2-ready` use the rebuilt current CLI, the configured `taotoken/deepseek-v4.1-flash-1017` model and a managed source-only browser entry limited to `browser_navigate`. Their disposable HTTP fixture records every request. Model credentials remain child-environment-only; saved account configuration contains an environment reference. No personal profile or OS grant is used, and no Chrome GUI is launched because approval is never granted.

Each run observes an actual `session/request_permission` with the exact fixture URL and a live owned backend, sends no permission response/cancel/close message, closes only stdin and keeps reading stdout. Both actual processes exit zero. EOF-to-exit is 5005.92ms / 5005.17ms, within the below-six-second envelope of the existing five-second bounded session stop. This does not claim every task naturally settled before the bound. Both native event logs contain exactly one error tool result, exactly one Cancelled terminal and no browser navigation ToolStarted. HTTP request counts remain zero. All captured owned PIDs are absent after exit.

A fresh actual ACP process then silently resumes and closes the same native session in each version. Both return zero, make no HTTP requests and leave the log byte-identical. This proves that pending permission EOF does not strand the native lease. Machine-readable `evidence.json`, raw `wire.json`, stderr, isolated configuration and native event logs remain under the two private fixture roots; their evidence records log SHA-256 and captured PIDs. Fixture HTTP servers were explicitly stopped.

The initial `/tmp/atomcode-acp-pending-stdio-v1` is a diagnostic, not pending-permission acceptance: the first model prompt arrived before asynchronous MCP catalog publication, the model returned normally without a browser call, and there was no permission request or HTTP effect. That completed no-tool diagnostic process was explicitly stopped; its failed evidence remains separate. Corrected independent fixtures wait for backend output preparation and initial discovery before the model prompt, then require the actual approval request as authoritative proof that the tool is available. This acceptance does not repair or claim first-prompt catalog-readiness behavior.

Final checks: all eighteen ACP end-to-end tests pass without skips (`/tmp/atomcode-acp-pending-regression.log`); `cargo build -p atomcode`, formatting/check and workspace compile gate pass (`/tmp/atomcode-acp-pending-build.log`, `/tmp/atomcode-acp-pending-compile.log`), including feature targets and negative canaries. Cargo.lock is unchanged; forbidden package counts are checked before submission. Only tests and documentation changed.

Pending-permission EOF on the recorded macOS stdio baseline is accepted. Manual editor rendering, broken-output/other transport faults, first-prompt MCP readiness, other-platform execution, GUI permissions and the full origin upload/CDP matrix remain outside this evidence and stay open in the overall goal.
