# ACP SDK 2.0 升级与协议支持推进路线

> 本文档为 ACP(Agent Client Protocol)支持的全量分析、差距评估与推进方案,是
> `atomcode acp` 子命令后续开发的对齐基线。分析基准:SDK `agent-client-protocol
=1.0.1`(schema 1.1.0)、官方文档
> <https://agentclientprotocol.com>(v1 稳定 + v2 draft)、SDK 2.0.0 源码与官方测试。

## 1. 目标

1. 将 `agent-client-protocol` 依赖升级到 2.0.0,并把现有 ACP 实现迁移到新 API,
   保持稳定 v1 行为不变;
2. 全面分析并补齐稳定 v1 协议中"应当实现但尚未实现"的能力;
3. 按官方建议(feature 门控、per-connection 协商)实现 v1 + v2 双协议支持;
4. 明确因架构冲突或客观约束"目前做不了 / 选择不做"的面,并说明理由。

## 2. 现状盘点

### 2.1 当前 ACP 实现(`crates/atomcode-cli/src/acp/`)

| 文件            | 职责                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------- |
| `mod.rs`        | ACP agent 装配(v1/v2 双链)、`serve_stdio`/`serve_over`、`protocol_router` 分流、fallback dispatch           |
| `engine.rs`     | 会话引擎:`EngineConfig` + `spawn_session`(prepare → assemble → spawn 出 `CodingRuntime`)                   |
| `dispatch.rs`   | `Sessions` 会话表、`session/new`、`session/prompt` turn 循环、`session/cancel`、resume/load/list/delete/close/set_mode/set_config_option |
| `permission.rs` | 审批回环:kernel `Request{kind:"approval"}` ↔ `session/request_permission`,v1/v2 独立 wire shape,fail-closed |
| `translate.rs`  | v1 事件映射:TextDelta/Reasoning/ToolStarted/ToolResult/PolicyIntervention/Usage → `session/update`;stop reason 映射 |
| `v2.rs`         | v2 draft 链:prompt 生命周期、事件映射、resume replay、config-option 边界转换、审批/elicitation 桥接         |
| `commands.rs`   | slash 命令广告与本地执行、v1/v2 plan update 派生                                                           |
| `elicitation.rs`| `request_user_input` ↔ `elicitation/create`(form)回环与 schema/应答映射,fail-closed                        |
| `replay.rs`     | resume/load 历史回放:原生聚合 → neutral replay entries(供 v1/v2 各自映射)                                  |

已实现的稳定 v1 方法(截至 2026-08-18,见 §9 增量记录;本节后续小节以最新为准):

- `initialize`:协商 v1,广告 `loadSession=true`、`prompt.capabilities.image=true`、`sessionCapabilities{list,delete,close,resume}`,携带 `agentInfo`;v2 路由经 `protocol_router` 分流;
- `session/new`:生成 `acp-<native-id>` 会话(wire id 与 native 持久化 id 双向还原),每会话独立 provider factory(不跨会话泄漏 gateway affinity),client 注入的 stdio/http MCP servers 接入工具目录,响应携带 modes/configOptions,随后广播 `available_commands_update`;
- `session/prompt`:turn 在 dispatch loop 外 spawn(保证 cancel/审批可并发处理),流式
  `session/update`(agent_message_chunk / agent_thought_chunk / tool_call / tool_call_update),
  图片走 vision,messageId 按"每次 LLM 输出轮"分配(每轮 `Usage` 事件推进),stop reason 精确映射(含 MaxTurnRequests 覆盖、SnapshotUnavailable 失败语义);slash 命令本地执行(无附件时);
- `session/cancel`(notification):只取消目标会话;未知会话为 no-op;
- `session/resume` / `session/load`:共享 `handle_resume_session` 恢复管线(校验 cwd 与 lease,失败 fail-closed);`load` 按 v1 规范重放全量历史(`session/update` 逐条推送),`resume` 静默恢复并回显 modes/configOptions;
- `session/list` / `session/delete` / `session/close`:list 合并活会话+原生 catalog 并 cursor 分页;delete 先关活会话再删持久化记录(未知会话静默成功,他进程 lease 冲突明确报错);close 取消+shutdown 并移出会话表;
- `session/set_mode` / `session/set_config_option`:mode 映射 `RuntimeMode` 并广播 current_mode_update;config option(model/mode/reasoning_effort)复用 runtime reload,广播 config_option_update;
- `session/request_permission`(agent→client):三选项(allow_once/allow_always/reject_once),
  任何异常 fail-closed 为 deny,且绝不因审批失败拆连接;
- plan / usage / message id:todowrite 派生 v1 `plan` update;usage→`usage_update`(used/size,cost 因无定价表不填);messageId 覆盖 v1(可选)/v2(必填),v1/v2 共享计数器;
- fallback:未知 client→agent request 回 JSON-RPC error,response/notification 直通内置 router。

已实现的 v2 draft 方法(截至 2026-08-19,见 §9 增量记录;与 v1 共享会话表/engine/provider factory/config catalog/message-id 计数器):

- `initialize`:回 `capabilities` + 必填 `info`;记录客户端 `capabilities.elicitation.form` 广告;
- `session/new` / `session/resume`:响应广告 `config_options`(v1 catalog 边界转换为 v2 形状,空时省略),随后广播 v2 `available_commands_update`;
- `session/prompt`:即时 `{}` ack → `state_update(running)` → 流式 message/tool updates → `state_update(idle, stopReason)`;messageId 必填并按轮推进;
- `session/set_config_option`:复用共享 `apply_session_config_option`,广播 v2 `config_option_update` 并返回完整 catalog;v2 无独立 current_mode_update(mode 变更经 config option 反映);
- `session/request_permission`(agent→client):独立 v2 wire shape(`title`/可选 `description`/`subject: tool_call`),fail-closed;
- `session/list` / `session/close` / `session/delete` / `session/resume`(+`replayFrom: start` 全量回放)、`session/cancel`、`$/cancel_request`;
- plan / 命令 / elicitation:todo 派生 v2 `plan_update`(稳定 planId,`PlanUpdateContent::items`);slash 命令走 v2 `Text` 输入;elicitation 复用 v1 wire shape(§9 已用跨版本测试固化:当前 v1/v2 wire 一致)。

已知限制(当前,2026-08-19):

- prompt 仅消费 text + image 内容块(audio/resource 忽略,未广告对应 capability);
- diff 内容块 / tool locations / usage cost 未实现(缺事件侧结构化来源;**diff 决定暂不实现**:kernel `ToolResult` 仍为字符串,按约束不修改 kernel 产出结构化 old/new,客户端继续从文本结果渲染);
- v2 的 `terminal_update` / `terminal_output_chunk`(agent 自持的 display-only 终端)未发射:kernel bash 工具无 PTY/字节流事件,只有字符串结果,归属 §4.3 的"做不了"面。

## 3. SDK 版本差距:1.0.1 → 2.0.0

crates.io 最新稳定版 `agent-client-protocol 2.0.0`(2026-07-23 发布;上游 1.2.0/1.3.0 为过渡)。

2.0.0 关键事实(来自官方 release notes 与迁移指南
<https://agentclientprotocol.github.io/rust-sdk/migration_v2.0.html>):

- **wire 层保持稳定 v1 schema 不变**;破坏性变更集中在 Rust SDK API 与传输边界;
- `agent-client-protocol-schema` 升到 1.5.0;draft v2 API 语义 newtype 化、diff/terminal 类型修订;
- `Channel` 携带 batch-aware `TransportFrame`(Single/Batch/malformed),不再直接收发裸消息;
- JSON-RPC API 角色化:`ResponseRouter.respond*` → `route*`;`Dispatch::respond_with_error`
  移除(改为 match 变体);`TypeNotification::new(message)` 不再带 connection;
- matcher:`if_message` → `if_dispatch`;`with_responder` → `with_runner`;
  `DynamicHandlerRegistration` → `DynamicHandlerGuard`(不再 Clone,`detach()` 取代 `run_indefinitely()`);
- request id 改借用语义(`SentRequest::id` → `&RequestId`);
- 2.0.0 将 `unstable_cancel_request`(协议级请求取消)、`unstable_boolean_config` 稳定化;
- `mutual` **v2 自动 wire 转换被移除**(`v2::conversion` 模块删除),改为显式双路由器
  `Agent.protocol_router().with_v1(..).with_v2(..)`,见第 5 节。

### 4.3 做不了 / 选择不做(及理由)

> 截至 2026-08-18 复核:以下判定仍然成立(`fs/*`、`terminal/*` 与 v2 已删除这些方法
> 的判定一致;`authenticate / logout` 仍保持空 authMethods;NES / MCP-over-ACP /
> Session fork / HTTP 传输 / v2 terminal 字节流仍为 draft 或依赖缺失事件源)。

| 面                                                            | 判定                 | 理由                                                                                                                                                                          |
| ------------------------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fs/read_text_file`、`fs/write_text_file`(agent→client)       | 不做                 | 与 kernel 单一状态所有权冲突:文件读写由 kernel/capabilities 单方持有,经审批/策略/纪律链路;再开客户端侧并行工具路径会分裂工具语义。且 **v2 已删除这些方法**                    |
| `terminal/*`(agent→client)                                    | 不做                 | 同上;bash 输出是 kernel 工具结果字符串,非客户端终端;v2 改为 agent 自持的 display-only 终端更新                                                                                |
| `authenticate` / `logout`                                     | 不做(空 authMethods) | 凭证在 config 层,provider 由 factory 构建为已认证实例(gateway 签名);无"编辑器登录"场景。暴露 authMethods 反而引入凭证经 stdio 传输的泄漏面;后续需求走 RFD `get-auth-state` 面 |
| NES(Next Edit Suggestions)                                    | 暂不做               | SDK 仍标 `unstable_nes`;需要客户端文档事件源 + agent 文档模型,kernel 无此事件源;编辑器协作循环投入产出比低                                                                    |
| MCP-over-ACP                                                  | 暂不做               | draft RFD;atomcode 是 agent 侧自集成 MCP(prepare 从 `.mcp.json` 拉起);"客户端工具经 ACP 注入"是另一套工具所有权模型,需在 kernel 新增远端工具面                                |
| Session fork                                                  | 暂不做               | draft RFD;kernel 有 snapshot 可支撑,但与 v2 resume `replayFrom` 的语义关系未定型,等 v2 定稿一起做                                                                             |
| HTTP/WebSocket 传输                                           | 范围外               | 规范自身 WIP;stdio 是 v1 唯一稳定传输;远程面落在 daemon 层,需独立 `agent-client-protocol-http` crate                                                                          |
| v2 terminal 字节流(`terminal_update`/`terminal_output_chunk`) | 暂不做               | kernel bash 工具无 PTY/字节流事件,只有字符串结果;需 kernel 终端抽象(大工程),真实价值待验证                                                                                    |
| v2 `tool_call_content_chunk`(工具输出逐块流式)                | 暂不做               | 同 diff/terminal:`AgentEvent` 仅有 TextDelta/Reasoning/Usage/Warning/ToolStarted/ToolResult,无工具输出逐块/字节流事件,`ToolResult` 为字符串;纯 CLI 无法在不动 kernel 的前提下产出该流,需 kernel 新增工具输出分块事件源(2026-08-19 复核)        |

## 5. v1 + v2 双支持机制(已确认可行)

两代 SDK 的机制不同,本方案以 2.0.0 为准:

- **1.0.1(旧)**:`Agent.v2()` 单 API surface,`ProtocolCompat` 在传输边界用 schema
  `v2::conversion` 自动做 v1↔v2 wire 转换;限制:一套 handler 链只能一种 API surface
  (merge 会 panic)。
- **2.0.0(目标)**:移除自动转换,提供官方正式路径 ——
  `Agent.protocol_router().with_v1(v1_agent).with_v2(v2_agent)`。
  路由器按客户端 `initialize` 的 protocolVersion 分流:请求 2 → 走 v2 实现,否则走 v1 实现;
  官方测试覆盖 `protocol_router_routes_v1_client_to_v1_implementation` /
  `protocol_router_routes_v2_client_to_v2_implementation` / v2-only 拒绝 v1 / 运行时开关。
- 结论:**可以同时支持 v1 和 v2**;代价是两套 handler 各自独立实现(官方迁移指南原话
  "implement v1/v2 handlers separately"),语义显式、无自动转换边角。

v2(draft)相对 v1 的要点:

- `session/prompt` 立即回 `{}`,进度/终态全部走 `state_update`(running / idle /
  requires_action,idle 携带 stopReason);
- v1 的 `session/load`、`session/set_mode` 移除 → `session/resume(+replayFrom)`、
  `session/set_config_option`;`authenticate`→`auth/login`、`logout`→`auth/logout`;
- capabilities 重组:`capabilities` + 必填 `info`,标记由布尔改为对象 `{}`,会话级能力
  嵌套在 `capabilities.session`;广告 session 时 7 个 session 方法为必选;
- `tool_call` 合并进 `tool_call_update`(首个 update 即创建,upsert 语义),新增
  `tool_call_content_chunk`;`plan` → `plan_update`(必填 planId + type 判别);
- 审批请求带必填 `title`、可选 `description`、tagged union `subject`(tool_call/command);
- 全量 messageId 必填;diff 改为 `changes` + `patch(git_patch)`;slash command `input`
  为带 `type:"text"` 的 tagged union;JSON-RPC batch 支持;枚举/open union 向前兼容。

## 6. 推进方案

### P0 — 本文档(交付物)

现状、差距表、放弃项理由、SDK 迁移清单、双支持设计、验证策略(即本文)。

### P1 — SDK 2.0.0 升级 + 全量 re-vendor

1. 根 `Cargo.toml`:`agent-client-protocol = "=2.0.0"`(维持精确锁定风格);
2. `cargo update -p agent-client-protocol`(连带 derive 2.0.0、schema 1.5.0);
3. `cargo vendor vendor/` 全量重新生成(需联网;vendor/ 未跟踪,不触碰已跟踪文件;
   不接入 source replacement,维持源码快照定位);
4. `cargo build -p atomcode-cli` 验证 lock/vendor 一致。

### P2 — 现有 ACP 实现迁移到 SDK 2.0 API(行为不变)

- `src/acp/mod.rs`:builder 接线迁新版;fallback dispatch 改
  `match Dispatch::Request(_, responder) => responder.respond_with_error(..)`;
  matcher 改 `if_dispatch`;
- `src/acp/dispatch.rs` / `permission.rs`:`Responder`/`SentRequest::id` 借用语义、
  `send_request(..).block_task()` 适配;
- `src/acp/engine.rs` / `translate.rs`:不涉传输 API,大概率不动;
- `tests/acp_end_to_end.rs`:duplex Channel 的 TransportFrame 语义、Client.builder 接线;
- 门禁:`cargo test -p atomcode-cli` + `cargo clippy -p atomcode-cli --all-targets`,v1 行为回归。

### P3 — 按序补全 v1(每项独立提交 + 测试)

1. `session/close` + 会话清理(修复已知泄漏);
2. `session/list`(活会话)+ capabilities 广告;
3. `session/set_config_option`(复用 runtime provider/model reload);
4. `session/set_mode`(映射 plan_mode);
5. plan 更新(先调研 coding 层计划事件源,有则映射,无则仅广告);
6. elicitation(开 `request_user_input` + `unstable_elicitation` + `elicitation/create` 回环);
7. usage/session_info + message id + slash command 广告(diff 内容块已决定不做,见 §9);
8. `session/resume` / `load` / `delete`:先写 mini 设计(ACP 会话 ↔ native SessionManager
   持久化归属,复用 kernel `resume_session`/snapshot),再实施。

### P4 — v1 + v2 双支持(draft,feature 门控)

1. cli 依赖开启 `unstable_protocol_v2`;
2. `Agent.protocol_router().with_v1(v1_agent).with_v2(v2_agent)` 按协商分流;
3. v1 实现 = P2/P3 之后的现有 handler 链(默认模式,优先保证);
4. v2 实现(`Agent.v2()` 独立链):prompt 立即 `{}` ack + `user_message(messageId)` +
   `state_update`;capabilities+info;tool_call_update-only + content_chunk;plan_update;
   审批 title/description/subject;config_option_update;resume replayFrom;
5. translate 层拆 v1/v2 两套事件映射;engine 共享(仅 wire 类型不同);
6. 测试:分别用 v1 客户端与 v2 客户端连 router,断言各自走对应实现(复用官方测试模式)。

## 7. 验证策略

- 每阶段:`cargo test -p atomcode-cli` + `cargo clippy -p atomcode-cli --all-targets`;
- P1 末:lock/vendor 一致;P2 末:v1 行为回归;改 workspace 依赖后跑一次 workspace 级
  build/test 确认仅 cli 受影响;
- 端到端:Python JSON-RPC stdio 冒烟脚本驱动 `atomcode acp`,覆盖 v1/v2 协商 →
  new → prompt → cancel → close;可选手工 Zed 验证;
- 交付报告:验证基线、各阶段结果、已知未验证范围。

## 8. 风险与边界

- SDK 2.0.0 发布仅约 1 个月,具体 API 以 vendor 源码为准(这正是保留 vendor 源码快照的原因);
- v2 是 draft,随规范演进随时变化 → 永远 feature 门控、v1 为默认;
- `session/resume` 触碰 native 持久化归属,单独设计,不与普通补全混做;
- 改动范围:仅 `crates/atomcode-cli/` + 根 Cargo.toml/lock + vendor/ + 本文档;
  不触碰其他 crate 与 driver;不恢复任何 core/bridge 兼容面。

## 10. session/resume|load|delete 持久化 mini 设计(①-⑤ 已实施)

**问题**:ACP 会话当前纯内存(进程内活会话表),`session/resume`/`session/load` 无来源,`session/delete` 只能删活会话。

**约束(AGENTS.md)**:native `SessionManager`(SessionMeta/SessionSnapshot/PresentationFile)是唯一 session 持久化模型;历史 core JSON 仅允许 daemon 私有 DTO 单向导入;kernel 已有 `CodingRuntime::resume_session` / `RestoreSnapshot` 能力。

**设计要点**:

1. **归属**:ACP 会话复用 native session 存储目录(与 CLI/daemon 同一 catalog),SessionId 与 native session id 建立显式映射(前缀或并存字段),绝不做第二套持久化模型;
2. **resume**:`session/resume`(v2,含 `replayFrom`)/`session/load`(v1)→ 查 native `SessionManager` 取 snapshot → `CodingRuntime::resume_session(id)` 复用恢复管线;`replayFrom:"start"` 以 `session/update` 回放历史;
3. **list**:`session/list` 从"仅活会话"扩展为"活会话 + 持久化会话"(SessionManager 查询),cursor 分页落在一个列表;
4. **delete**:v1/v2 `session/delete` 升级为删持久化记录(活会话先 close);success/unknown 语义与当前一致;
5. **失败语义**:snapshot 缺失/损坏 → 明确错误,不静默 fresh;恢复失败回滚到可启动状态;
6. **测试**:manager 集成路径 + resume 回放 + delete 两侧;统一 tempdir 策略隔离 CLI/daemon 会话目录。

**实施顺序**:① SessionId↔native id 映射与 catalog 归属 → ② resume/load → ③ list 扩展 → ④ delete 持久化 → ⑤ v2 replayFrom。
