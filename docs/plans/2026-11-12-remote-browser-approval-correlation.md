## Delivered behavior and compatibility

PermissionResponders now keeps the sender and optional pending identity under one routing lock. Registering/replacing a sender or beginning a pending request creates no reusable queued grant; each request gets a new UUID, including when the provider reuses its tool call ID. Wrong/missing/duplicate answers leave a current pending question intact or return false after it has gone. Project and persistent grants use the same claim. Native tool call IDs and session persistence remain unchanged; only daemon HTTP approval routing receives the additional field.

The runtime captures the expected identity before publishing the request, preventing a fast answer from consuming the route before the expected token is captured. It clears the route after waiting and independently checks identity and already-requested cancellation before persisting a grant or responding. Already-queued approval and structured-input waits still observe an already-set cancellation token; they no longer disable their inner cancellation branch merely because the outer event loop saw cancellation first. The existing runtime cancel/terminal path remains authoritative.

Every /chat permission_request now carries approval_id alongside session_id/call_id. Every /chat/permission choice, including deny, project save and persistent MCP approval, must echo both IDs. Missing fields deserialize but return success=false and do not dispatch or queue a decision. Older clients must be upgraded with the daemon; there is no session-only fallback. WebUI card completion and VSCode response acknowledgements also carry the one-shot ID so an older response cannot close/approve a newer card reusing the provider call ID. JetBrains no longer auto-approves explicit daemon requests using its incomplete local tool-name list, and its Always choice maps to persistent MCP approval only for MCP tools, ordinary always_allow for other tools.

There is one held request in the accepted cancellation scenario. SSE disconnect deliberately does not mean automatic cancellation; the daemon retains the operation for recovery and explicit stop.

Main acceptance session 8fec1bb3-1ec4-486f-a0c7-c253be393eaf records normal positive/deny terminals and Cancelled terminals for disconnected-pending and dispatched cases.
