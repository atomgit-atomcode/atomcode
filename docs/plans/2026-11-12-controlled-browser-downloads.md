# Controlled browser downloads implementation plan

**Goal:** Add a backend-owned HTTP(S) download publication boundary before enabling per-origin download grants.

**Architecture:** The external browser backend owns transfer jobs and artifacts; CodingRuntime remains the sole agent owner. Chromium implicit downloads stay disabled. Every redirect must pass explicit access and download permission checks before a request, and only complete bounded responses reach generated artifact paths. Failed or cancelled transfers never retry automatically.

**Tech stack:** Node built-ins, node:test, existing optional MCP backend.

Baseline: release/v5.2.7 at 7d6eb260fcc0ec9382a965200a5ba3d1241bc802, clean worktree. Local Codex 806d9732c9 config/browser_use.rs separates access/downloads/uploads/full_cdp_access. ADR 0032 rejects cancellation-only download enforcement.

1. Add `integrations/browser-origin-scope/transfers.test.cjs`: positive artifact hash, permission denied before dispatch, redirect permission refusal, size limits, truncated responses, cancellation and cleanup, no replay, generated filenames.
2. Implement `transfers.cjs`: explicit policy callback, manual redirects, bounded identity-encoded streaming, private staging, exclusive atomic publication, transfer cancellation and permanent shutdown. Initial transport is unauthenticated HTTP(S); no caller headers, credentials, paths or browser cookie forwarding. Unsupported content encoding is rejected. Errors omit URL/query details.
3. Review tests and implementation together. Run existing v1 policy regressions. Keep the module unexposed until MCP cancellation, scoped policy v2, and browser context authentication receive integration tests.
4. Integrate through `policy.cjs`/`backend.cjs`, add managed CLI configuration and actual-browser tests in subsequent verified units. Upload/CDP, blob downloads, real UI and other-platform acceptance remain open in the full delivery audit.

Failure semantics: cancellation before synchronous publication removes staging and publishes nothing. Once the exclusive link succeeds, the artifact is committed; lost responses are uncertain outcomes and must not cause replay. Close aborts and awaits owned jobs. No browser event cancellation is treated as authorization.

## Explicit browser-cookie authentication unit

Baseline b031022ac726b055aae8d9b4663b05654a7051a7, clean release/v5.2.7. Reviewed publisher dispatch/cancellation, owned browser lifecycle, schema/doctor and public installed Playwright BrowserContext.cookies API. Local Codex remains the policy vocabulary reference; no web executor is inferred.

Add an explicit `use_browser_context` boolean, default false. Authorization must precede any context lookup; true requires an existing owned context and captures that context rather than launching/replacing/importing a browser. Read destination cookies anew after each authorized redirect through the public API, additionally filtering domain/path/secure/expiry, refusing malformed/oversized headers and excluding partitioned cookies without an established partition context. Never expose cookie/header values in tool results, errors, metadata or config. Cancellation while reading credentials must stop dispatch and must not switch to a replacement context. Cookies are read-only in this unit: response Set-Cookie synchronization, HTTP authentication, partitioned authentication and other unsupported mechanisms remain explicit unfinished work; no retry on an auth failure.

Test default/no-context denial, no context read before grant, cookie/header scope, authorized cross-origin recomputation, cancellation during credential lookup, and actual isolated Chrome login/protected-download/denied redirect/close behavior. Keep existing v1/v2 download and process acceptance unchanged. Auth values are owned ephemeral fixture values, never personal credentials. No new dependency or runtime owner.

Explicit-cookie result: 37/37 standard-library tests pass, including cancellation both before context lookup and during cookie lookup, plus existing-context generation/close fencing. ## Native response-cookie synchronization unit

Baseline 8363ffa106fbcb7791fb3303f88f0f3a54e55f54, clean release/v5.2.7. Reviewed publisher response/cancellation, owned context fencing, public Playwright route.fulfill and cookie APIs, and recent related history. A private real-Chrome prototype (`/tmp/atomcode-cookie-sync-prototype.json`) proves that a fully intercepted empty response processes multiple Set-Cookie headers, HttpOnly/Secure/Path, invalid-domain and __Host prefix rules while retaining the original page. No maintained cookie parser is already installed, and direct addCookies would bypass part of normal HTTP validation; do not replace Chromium's cookie engine with an ad hoc parser.

Add explicit `sync_response_cookies:true`, requiring `use_browser_context:true`; existing read-only calls stay read-only. For each authenticated upstream response, feed only its bounded raw Set-Cookie headers into an empty, no-store/CSP-sandboxed response on a temporary page in the captured context. The page routes every request: exactly the source URL's first main-frame GET is fulfilled locally and all others abort. There is no second remote request, response code/body execution or origin override. Chromium itself enforces cookie attributes/public suffix/prefix/secure-overlay/expiry rules. Await temporary page disposal. Any uncertain synchronization failure or in-flight cancellation closes the captured owned browser through its existing owner; never adopt a replacement or retry the GET. Cookie effects already applied at headers are not rolled back on later body failure or cancellation.

The backend remains the sole browser/transfer owner; temporary pages belong to the transfer job. The private helper receives only internal context/url/header/signal data, not a new tool or model code/CDP surface. Test both response-cookie state and lifecycle/zero-replay behavior, including redirect rotation, deletion, invalid scope/prefix, original-tab preservation and cancellation. Keep partitioned-cookie reads, HTTP auth, blob/compression, upload/CDP, native runtime/remote fault and platform/GUI work open.

Response-sync findings and result:

- The native interception path preserves the recorded ordinary cookie semantics but **does not preserve Partitioned** on this pinned runtime: `/tmp/atomcode-native-cookie-sync-partition-diagnostic.json` and the origin-preserving sandbox variant both record `stored:true, partitionKey:null`. This is an unsafe negative control, not a supported implementation. All owned processes were reaped. Production now refuses Partitioned response batches before any temporary page/mutation; full partitioned support remains an explicit overall requirement.
- Native navigation also generates allowed-source speculative CONNECT attempts before fulfillment. A per-target offline/CDP trial still recorded eight CONNECTs and was removed. No new raw CDP surface or global offline toggle remains. The acceptance contract proves no **remote HTTP GET replay**, not zero TCP attempts; the same exact-origin proxy still enforces transport destinations.
- `/tmp/atomcode-native-cookie-sync-accepted.json` passes seven native groups on Chrome 157.0.8103.78/Node 22.22.0: scope/default path/HttpOnly/Secure/SameSite, foreign/public-suffix/prefix/oversize rejection, insecure secure-cookie overlay prevention, rotation/Max-Age deletion, Partitioned refusal, original page/disposal and actual in-flight native cancellation. An explicit replacement is empty; late old cleanup cannot close it. Twelve captured Chrome descendants are gone. The ordinary helper phase records zero forwarded HTTP/WS requests and eight allowed CONNECT attempts; these are different measures. Report integration hashes match current helper/backend/publisher/verifier sources.
- `/tmp/atomcode-cookie-sync-wire-delivery.json` passes thirteen MCP/real-Chrome groups, including HTTPS Secure response-cookie synchronization, redirect rotation/deletion visible in the original browser, old read-only behavior, original tabs retained, one remote GET per hop, Partitioned refusal without mutation/publication, a denied redirect retaining its authorized source cookie effect, auth cancel/close/EOF and no forbidden HTTP requests. No source Cookie/Authorization/Secure-over-HTTP leak is observed; all eight captured owned PIDs are gone and stderr is empty.
- Existing v1 actual browser verification passes nine groups again (`/tmp/atomcode-cookie-sync-v1-regression.json`), zero forbidden TCP connections. All 45 fast tests pass (`/tmp/atomcode-cookie-sync-tests-verified.log`). Formatting/check and complete workspace/feature/negative-control compile gates pass (`/tmp/atomcode-cookie-sync-compile.log`). No Rust source, dependency manifest, package lock or Cargo.lock change is involved.

Temporary pages are job-owned resources inside the original browser owner. `closeCaptured` uses context/opening identity and the owner's existing cleanup promise, never a second browser owner. Both argument flags are explicit, preserving old read-only calls and approval previews. Cookie effects can precede a failed file/body result and are not falsely treated as transactional. Partitioned/HTTP auth, blob/compression, upload/full-CDP, native runtime/remote faults and remaining GUI/platform acceptance are not completed by this unit.
