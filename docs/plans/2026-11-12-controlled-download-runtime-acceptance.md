# Controlled download runtime acceptance

Baseline: `release/v5.2.7`, `af9a4f903ca090f3ff756f8ee19b8b41a1be6fe0`, clean worktree. Current host scripted-provider tests, managed v2 policy-file setup, runtime Cancel/turn terminal and existing browser approval denial were inspected, together with recent host test history. CodingRuntime remains the sole lifecycle owner. This change adds acceptance tests, not an alternative runtime, hook or cancellation mechanism.

The actual MCP download verifier now exercises HTTPS first-party Partitioned response rotation across a redirect, exact generated artifact bytes/hash, deletion and a following request proving credential absence. It verifies original tabs stay unchanged and every remote hop executes once. Fixture CA trust is supplied only to its child backend. The report `/tmp/atomcode-partition-mcp-positive.json` passes fourteen groups with zero stderr, no denied requests and no staged remnants; EOF disposes the observed process tree.

The new opt-in host test uses the real configured backend, production registry/adapter and CodingRuntime with a deterministic scripted provider. A v2 access/download policy is installed through the normal managed setup. Ask-mode denial must reach a terminal without ToolStarted or any local HTTP effect. A second turn receives a per-call grant. The server independently records the request, sends only a partial body and withholds the remainder. Only after that observation does the driver send Cancel. The runtime must emit cancellation and exactly one turn terminal; releasing the late body must not trigger another request or publish a file. Both generated files and staging must remain empty.

This is controlled-provider runtime acceptance, not real-model reasoning, editor GUI rendering, remote transport fault acceptance, or proof that a cancelled remote server rolls back its effects. The independently observed request remains an effect; it must not be replayed. Existing manual real-model browser cancellation evidence remains separate.

The first runtime fixture used an invalid approval response (`allow_once` instead of the public `allow`) and correctly dispatched nothing; that diagnostic is `/tmp/atomcode-runtime-download-cancel.log`. Correcting the fixture exposed a production gap: `/tmp/atomcode-runtime-download-cancel-fixed.log` fails because one generated artifact is present after cancellation and late body release. The existing synchronous request guard correctly marks the client uncertain, but the registry's awaited turn-end cleanup filtered out unscoped clients, leaving their owned backend alive.

The fix uses the already-mounted `McpScopeFinish` / `TurnFinishing` listener, reached before the kernel's `TurnComplete`; no overlapping hook is added. Registry turn cleanup captures all clients rather than only lease-negotiated clients. Healthy unscoped/stateless clients retain their no-op path. An unscoped stdio client with an abandoned dispatched request closes its existing input, drains/reaps its owned process through the existing bounded teardown and keeps the uncertainty marker. It neither spawns a replacement nor clears the failure. Lease-negotiated clients retain their addressed cleanup; HTTP's remote effects remain unknown and its default turn cleanup is a no-op. Cleanup snapshots and existing replacement identity checks prevent late old failures from contaminating a new client.

A focused transport unit additionally proves that a healthy unscoped process survives turn completion, an abandoned process observes EOF before cleanup returns, its failure stays visible, stale calls fail, and repeated cleanup cannot restart it. The runtime fixture proves the complete cancellation path without depending on the unit's injected marker.

Full coding regression follow-up: the pre-existing `cancelling_a_dispatched_mcp_call_requires_reconnect_and_keeps_the_session` criterion still asserted a zero-wait native turn terminal and allowed only one virtual second. That contradicts the new requirement to retire an uncooperative owned backend before the terminal. The criterion now keeps the real subprocess clock running during bounded kill/reap, separately requires a prompt cancel receipt, bounds the terminal below five seconds (rather than the ten-second RPC timeout), and checks the captured backend PID is absent before terminal observation completes. Session identity, unknown-result failure, single initial dispatch, explicit reconnect and exactly one new requested call remain asserted. The first adjusted fixture retained a redundant clock resume and failed with `time is not frozen`; that fixture error was removed. `/tmp/atomcode-mcp-runtime-cancel-cleanup-fixed.log` passes the corrected criterion in 2.33 seconds. Production lifecycle behavior is unchanged by this test update.
