## 一、一句话

**屏幕仍然只握一个会话；握多个 runtime 的是宿主。** 交接文档说「要先做屏幕同时握住
多个会话」——那是 tuix 的做法（2351 行的后台槽管理在前端里）。新栈里屏幕跟一个会话
走、换会话就是 `HostEvent::SessionChanged` → `follow` → `Subscribe{from:0}` 重放，这条路
`/resume`、`/new` 天天在走。所以 `/bg` 不动屏幕的「一个屏幕一个会话」，而是让宿主
（`atomcode-cli`）手里有**一个前台 runtime + 至多 16 个后台 runtime**，换前台就是换
屏幕跟的那条流。

## 二、谁拥有什么

| 东西 | 拥有者 | 说明 |
|---|---|---|
| 每个 runtime 的生命周期 | 它自己的 `CodingRuntime`（各自一个 `CodingRuntimeHandle`） | 后台会话**不是**前台 runtime 里的第二个会话，是另一个 `CodingRuntime`，各有各的 `FrontEnd`、App、会话租约。ACP 早就在一个进程里跑多个 runtime（`acp/sessions.rs::register_session`），这里是同一个形状 |
| 「哪个在前台、哪些在后台」 | `atomcode-cli/src/background.rs` 的 `Background`（新） | 只管**槽位表**与**转发**：屏幕的命令流/事件流/宿主事件流转给前台那一个；不持有也不重建任何 runtime 的 provider/session/config。每个 runtime 仍由各自的 `RuntimeControl`（`host.rs`，`connect` 出来的）驱动 |
| 新 runtime 怎么起 | 启动器传进来的 `Spawn`（`main.rs` 用 `spawn_native_cli_runtime`，测试用脚本 provider） | 与启动时同一条装配路径，不另建第二套装配 |
| 会话内容 | 各自的事件日志（ADR 0024） | 回到前台时屏幕从日志重放，**不在宿主里缓存事件**；唯一缓存的是「挂着没答的那个 `Request`」——它不是日志事实，重订阅不会重发 |

**不是第二个生命周期 owner**：`Background` 不调用 `fresh_session`/`resume_session` 去
「在同一个 runtime 里换会话」，也不替任何 runtime 做 reload/cd/goal；它只决定屏幕现在
跟谁说话，以及在 `/bg drop`、退出时调用该 runtime 自己的 `cancel`/`shutdown`。

## 三、契约（`atomcode-host-api`）

新 `HostCommand`（后台会话是宿主概念，不是 coding 专有——daemon 迁契约（F3）时照着实现
即可，所以走契约而不是 cli 私有的命令行）：

| 命令 | 寻址 | 回答 |
|---|---|---|
| `Background { session }` | 前台 | `Backgrounded { session: 被放到后台的, slot }`；前台换成新的空会话（`SessionChanged` 事件） |
| `BackgroundSessions` | 否 | `BackgroundSessions { sessions }` |
| `Foreground { session, target }` | 前台 | `SessionChanged { session: target }`；原前台**有对话**就进 target 腾出的槽位，**空的**就关掉（不留一堆空槽） |
| `StartBackground { text }` | 否 | `Backgrounded { session: 新的, slot }`；前台不变 |
| `TellBackground { target, text }` | 否 | `Done`；给后台会话发一句话，不切过去 |
| `DropBackground { target }` | 否 | `Done`；跑着的先 `cancel`，然后 `shutdown`（放掉租约） |

新 `HostEvent::BackgroundChanged { sessions }`：槽位增减、后台回合结束、后台来了问题时推。
`BackgroundSession { session, title, state, created_at, last }`，`state` ∈
`Running / Waiting / Idle / Done / Cancelled / Failed`，`last` 是给面板那一行摘要用的一句
（等人时是那个问题、出错时是错误、否则是最后一段回答）——都从该会话**自己的日志**和
它的 runtime 事件读，不另存。

`/resume <后台会话的 id>` 被宿主改读成 `Foreground`：租约本来就会拒绝同一会话被开两次，
与其说「在用」，不如把它带回来。

只实现 `RuntimeControl`（单 runtime，ACP 也用）的宿主对这几条答「不支持」——这是真话：
没有 `Spawn` 就起不了第二个 runtime。

## 四、屏幕（`atomcode-tui`）

- 命令：`/bg`（=`Background` 然后开面板）、`/bg list`（开面板）、`/bg <N>`、`/bg drop <N>`、
  `/background <任务>`。`N` 是面板/列表里的序号，屏幕先问一次 `BackgroundSessions` 再换成 id。
- **面板**（不是 overlay）：照 resume/providers 的骨架——`crate::bg`（数据 + 纯函数 `key`
  + `Step`）、`crate::modules::bg`（画）、`Moment.bg`/`bg_panel`、`host.rs` 的
  open/close/show/key 方法与 `TAIL` 登记、`plugin.rs` 的按键路由与 `Action::OpenBg`、
  cli 的 `tui_bg.rs` 行（只挂画法）。**没有单独的端口**：面板的每个动作都说成一条命令
  （enter / esc → `/resume <id>`，宿主改读成 `Foreground`；输入框 → `/background <任务>`；
  space → `/bg tell <id> <话>`；ctrl+x → `/bg drop <id>`），面板和敲命令走同一条路。
  - 顶行：「你的对话已移到后台 — enter 打开 · esc 回到它 · ctrl+c 两次退出」；
  - 三组，顺序固定：`Needs input`（Waiting/Failed，黄 `✱`）、`Working`（Running）、
    `Completed`（Idle/Done/Cancelled，绿 `·`）；每行标题按组内最宽对齐 + 一行摘要，
    超宽截断；选中行整行底色、标题加粗；
  - 底部输入框，占位「describe a task for a new session」：回车 = `StartBackground`；
  - 按键：↑↓ 移动；enter 打开选中（`Foreground`）；esc 回到打开面板时的那个会话
    （由 `/bg` 打开的就是刚移走的那个 → `Foreground` 它；由 `/bg list` 打开的就是关面板）；
    space 就地回复选中（输入框变成「回复 <标题>」，回车 = `TellBackground`）；ctrl+x 删除
    （= `DropBackground`）；`?` 在输入框空时展开按键说明；ctrl+c / ctrl+d 不被面板吞，照常退出。
- 状态靠 `HostEvent::BackgroundChanged` 推，不轮询。

## 五、拒绝与终态

每个被接受的操作都有终态；失败一律**什么都没动**：

- `Background`：前台在等人回答（`WaitingApproval`）、正在重建（`Reconfiguring`）→ `Busy`；
  正在共享（`/webui`/`/sync`，hub 绑着前台的句柄）→ `Busy`；槽满 16 → `Busy`；新 runtime 起不来
  → `Failed`，原前台原样不动（新 runtime 起好之前不碰槽位表）。
- `Foreground`：target 不在槽里 → `NotFound`；共享中 / 前台在等人回答 → `Busy`。
- `StartBackground`：起不来 → `Failed`；起来了但 `submit` 被拒 → 关掉这个新 runtime 再报错，
  不留一个没任务的槽。
- `TellBackground`：runtime 拒收（例如在等审批）→ 原话报回。
- `DropBackground`：不在 → `NotFound`；`cancel` 失败不挡 `shutdown`；回答在 `shutdown`
  返回之后给（租约此时已放）。
- **后台回合要人回答**：它等着（不自动批准，与 tuix 一致），状态 `Waiting`，面板归入
  `Needs input`；回到前台时屏幕重订阅，宿主在重放之后把那条 `Request` 再发一次。
- **迟到事件**：每个 runtime 的事件只有它是前台、且屏幕已经重新订阅了它之后才转给屏幕；
  换前台那一刻前一个 runtime 还在路上的事件被丢掉——它们在它自己的日志里，下次回来重放。
- **退出**：屏幕的 `Shutdown` 转给前台，同时对每个后台 runtime `cancel` + `shutdown`，
  `tui_front::run` 等它们都停了才返回。tuix 退出时是直接丢掉后台槽（进程结束，回合被
  腰斩、半截没落盘）；这里改成显式取消，半截回复作为 `PartialReply` 事实落进日志，
  之后可以 `atomcode resume <id>` 接着聊。退出时不额外询问。

## 六、租约

- 每个后台会话一直持有它自己的租约，放到后台不放、回到前台不换（同一个 runtime）。
- 前台 `/resume` 一个后台会话：见 §三，改读成 `Foreground`，不会同一会话开两份。
- `/resume` 列表、删除：后台会话的租约被占，`DeleteSession` 照旧答 `SessionInUse`。

## 七、判据（都写成测试，先摘掉被测代码证红一次）

端到端在 `crates/atomcode-cli/tests/tui_bg.rs`（真屏幕 headless + 真 runtime + 脚本 provider，
provider 收到「slow」时卡住直到测试放行、收到「ask me」时用 `request_user_input` 问一句）。
每条括号里是证红时摘掉的东西，都实测红过一次：

1. `a_turn_keeps_running_after_bg_and_its_result_is_there_on_return`：回合跑着时 `/bg`，前台
   换成新的空会话（日志里没有那句话）；面板真渲染一帧，`进行中` 下有它，放行后挪到 `已完成`；
   esc 回到它，屏上有那段回答；换下来的空会话被关掉、不占槽。
   （`/bg` 时取消旧 runtime → 红；`TAIL` 不登记面板 → 红；esc 改成只收面板 → 红；
   `/resume <后台会话>` 不改读成 `Foreground` → 红。）
2. `bg_drop_cancels_a_running_one`：ctrl+x 丢掉跑着的后台会话，放行后模型那一句从没做完、
   日志里没有，槽位没了。（drop 里不 cancel+shutdown → 红。）
3. `background_task_runs_without_changing_the_foreground`：`/background <任务>` 后屏幕还跟原会话，
   后台会话做完、日志里有回答；`/bg 1` 把它带过来。（不 submit → 红。）
4. `a_task_typed_into_the_panel_starts_a_background_session`：面板输入框里写任务回车。（同上 → 红。）
5. `a_question_asked_in_the_background_is_asked_again_on_return`：后台会话在等人回答，状态
   `Waiting`、那一行是问题；`/bg 1` 回来后问题真的在屏上可答（回车选第一项，回合继续）。
   （重订阅后不重发挂着的 `Request` → 红。）
6. `space_in_the_panel_replies_without_switching`：space 就地回复，话进了那个会话、屏幕没换。
   （`TellBackground` 不 submit → 红。）
7. `bg_is_refused_while_a_question_waits`：前台在等人回答时 `/bg` 答 `Busy`，什么都没动。
   （摘掉 `WaitingApproval` 那一条拒绝 → 红。）
8. 纯函数单测：`atomcode-tui/src/bg.rs`（按键）、`modules/bg.rs`（分组顺序、对齐、占位）、
   `atomcode-cli/src/background.rs`（回合结局 → 状态、问题随回合结束作废）；契约样例表
   （`host-api` 的 exhaustive 表）。

## 八、不做 / 以后

- 后台回合的 OS 通知沿用 `connect` 里已有的（回合结束、等人时都会通知）。
- 退出时不打印每个后台会话的 `resume` 提示（启动器现在只打印启动时那个会话的，本就不准，另议）。
- 面板不接鼠标（点行、滚轮）；`?` 只是把图例换成完整按键说明。
- 退出（`Shutdown`）停后台 runtime 这一条没有端到端判据：`tui_front::run` 之后进程就结束，
  测试台里没有可观测的东西；它是 `Background::shutdown_all`，与 `/bg drop` 共用 `stop`。
- daemon / ACP 不实现这几条命令（ACP 本身就是一 session 一 runtime）。
