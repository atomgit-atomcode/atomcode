# 一次性后续任务

主 CLI/TUI/WebUI 支持用户预设的一次性同会话 follow-up：

```sh
# Headless：两步都执行结束后才返回最终退出状态
atomcode -p '实现这个修复' --follow-up '检查刚才的修改，补跑必要测试并总结'

# TUI / WebUI 输入框
/followup set 检查刚才的修改，补跑必要测试并总结
/followup show
/followup clear
```

空闲时登记，作用于下一次通过普通消息入口提交的人工任务；运行中登记，作用于当前任务。通知、自动输入和本地命令不会领取空闲登记。若希望接在技能/目录命令唤起的任务后，请在该任务运行时登记。重复 set 替换原登记。prompt 最大 16 KiB UTF-8，不允许空白。登记后再次提交人工输入会撤销已经绑定当前任务的旧登记，以新指令优先。

只有正常停止、没有待答请求/未收取的后台任务、持久化没有失败时才执行。取消、错误、预算耗尽等终态不执行；相应登记被消费或清除，不会在以后的任务上突然触发。这里的“正常结束”不是业务成功判定，不能据此推导“测试通过，所以可以部署”。

后续 prompt 在同一会话、相同模型和权限模式下执行，正常经过 hooks、工具权限和审批。权威历史中的输入带“Automatic follow-up / 自动后续任务”标识，执行前也会显示提示。它是用户预设输入，会应用现有的每轮执行限制；不会升级权限。原任务与 follow-up 作为一个受管理操作完成，headless 调用会等待两步结束，退出状态反映最终执行终态。

登记在提交后续输入之前即被消费；后续任务不会因为自己的完成而再次触发它。goal/loop 与待执行的 follow-up 互斥，需先停止 goal/loop 或撤销登记。取消、会话/目录切换以及导致 generation 改变的 runtime 重建会清除登记。

待触发登记只在当前进程保存，不支持重启恢复、定时任务链、条件分支或持久 DAG。新会话 action 见下文。WebUI 只管理当前已绑定的会话，浏览其他历史会话不会改绑运行时，也不能为它登记。

## 新会话后续任务

使用 `/followup new <JSON>` 登记一次性新会话任务。它与 `set` 共用一个登记位置，后一次登记替换前一次。示例：

```text
/followup new {"prompt":"审查刚才提交的修改","permission_mode":"plan"}
/followup show
/followup history
/followup history followup-<执行 ID>
```

可选字段：`cwd` 为已有绝对目录，默认登记时的工作目录；`model` 为配置中的模型选择 ID，默认登记时当前模型选择；`permission_mode` 只允许 `plan`（默认）或 `accept_edits`。`context` 是用户显式提供的参考文本（最大 64 KiB UTF-8），默认不传任何历史。系统不会自动拷贝原会话、摘要或最后回复，也不静默截断。参考文本通过独立 context 通道提交，预设 prompt 保持真实用户输入的执行限制语义。

CLI 可将上述 JSON 保存为 UTF-8 文件：

```sh
atomcode -p '实现修复' --follow-up-new-file follow-up.json
```

`--follow-up-new-file` 与 `--follow-up` 互斥。CLI/TUI/WebUI 都通过同一个 runtime 登记入口；TUI/WebUI 的 `show` 显示新会话目标、权限与执行 ID。已登记任务只在原任务正常结束且无待处理工作后启动。原任务正常结束不等于测试通过，不适合直接表达“测试通过才部署”。

新会话由现有自动化 worker 独立执行，不改绑前台会话，不广播原会话的切换，也不复制原会话的审批授权。沿用无人值守审批：需要人工批准的操作会被拒绝，不能使用 `auto` 绕过。新会话按现有自动化会话标记展示，可从会话列表打开；执行记录关联原会话与新会话，聊天原文仍由新会话的 native `.events` 保存。

原 CLI 调用在启动结果返回后结束，其退出码只代表原任务，不代表独立新会话执行成功。请用 `history <执行 ID>` 查询新任务终态。列表显示最近 20 项，详情返回最近 50 条执行事件与分页游标。启动回执区分 `accepted`、`failed`、`uncertain`；accepted 仅代表 worker 已启动。遇到 uncertain 不自动重试，应先检查记录和目标会话。

启动复用现有自动化 admission、请求去重、租约和历史基础设施，记录放在产品目录的 `followups/`，不混入定时任务列表，也不注册 OS 定时器。执行 ID 在登记时生成，启动前持久化任务及回执，worker 只接受原 ID 与精确版本；已经领取的 ID 不会再次执行。进程重启前尚未触发的登记不恢复；已启动 worker 独立继续，`clear` 只撤销尚未启动的登记。此版本不提供条件分支、DAG、自动重试或定时任务后处理。
