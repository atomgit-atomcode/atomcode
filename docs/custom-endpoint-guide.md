# AtomCode 接入自定义 OpenAI 兼容大模型端点实战

> 本文档适用于：想在 AtomCode 里接入任意 OpenAI 兼容协议的大模型服务（自建 vLLM、第三方推理云、兼容网关等），但不确定怎么填 Base URL / API Key / 模型名，或遇到 503 / 模型不存在等报错的场景。基于真实踩坑整理。

## 1. 前置条件

- 一个暴露 OpenAI 兼容 Chat Completions 接口的服务地址，形如 `https://your-host/v1`
- 该服务签发的 API Key（形如 `sk-xxx` 或服务商自定义字符串）
- 该服务支持的具体模型名（必须与服务端注册的一致）

> ⚠️ AtomCode 只认 OpenAI 兼容协议。如果服务商给的是专有 SDK，需要先套一层兼容网关（如 LiteLLM / One API）。

## 2. 在 AtomCode 中配置

以「自定义 API」提供商为例：

| 字段 | 填写内容 | 说明 |
|------|----------|------|
| 提供商 | 自定义 API / Custom | 选支持填 Base URL 的类型 |
| Base URL | `https://your-host/v1` | 不要手动追加 `/chat/completions`，AtomCode 会自动拼接 |
| API Key | 你的 Key | 直接从服务商后台复制 |
| 模型名称 | 服务端注册的精确模型名 | 见第 3 节「模型名不匹配」 |

配置保存后，先发一条测试消息确认能正常返回。

## 3. 常见坑与排查

### 坑一：503 / "connection pool exhausted"
- **含义**：服务端过载或连接池耗尽，不是你网络问题（能收到 503 说明已连到服务器）。
- **解法**：等几分钟到半小时重试；免费/共享算力池在晚高峰尤其易触发。
- **排除**：不是"需要科学上网"——503 是服务器主动返回，网络不通会是超时/DNS 错误。

### 坑二：400 / "model not supported" / "model not found"
- **含义**：模型名服务端不认。
- **解法**：
  1. 核对服务商文档里的精确模型字符串（大小写、连字符、组织前缀如 `org/model` 都可能要）
  2. 有些平台要求带组织前缀，如 `zai-org/GLM-5.2`；先试裸名，报错再试前缀
  3. 确认你的权益档位包含该模型（免费档常只开放部分模型）

### 坑三：Base URL 多写了路径
- 错误：`https://your-host/v1/chat/completions`
- 正确：`https://your-host/v1`
- 多写的路径会被二次拼接导致 404。

## 4. 把推理成本压下来：上下文缓存优化

OpenAI 兼容服务普遍支持前缀缓存（Prompt Cache）：当多次请求的输入前缀从第一个 token 起逐 token 一致时，命中部分按约 1/50 计费。

### 利用规则
1. **稳定长文本放最前且一字不改**：系统指令、工具 schema、固定背景说明——这些是你每次请求都带的前缀，一旦稳定即可高频命中。
2. **变量（当轮问题）放最后**：每轮变化的内容放消息尾部，坏掉也不影响前面命中。
3. **别在头部放时间戳 / request_id / 随机 UUID**：会破坏前缀一致性，导致每次全价 miss。
4. **同一服务内切换同系列模型**通常共享缓存；跨供应商则各自冷启动。

### 验证命中率
每次响应带 `usage` 字段：
- `prompt_cache_hit_tokens`：命中缓存的 input token 数
- `prompt_cache_miss_tokens`：未命中的

命中率 = hit / (hit + miss)。命中价约为未命中的 1/50。

### 跨客户端注意
同一个 Key 下，不同客户端各自注入不同的系统提示与工具 schema，前缀从 token 0 就分叉，缓存不互通。应在每个客户端内部分别保持前缀稳定。

## 5. 验证清单

- [ ] 用精确 Base URL（不带 `/chat/completions`）能连通
- [ ] 模型名与服务端注册完全一致
- [ ] 发两条相同前缀的请求，第二次 `prompt_cache_hit_tokens` > 0
- [ ] 高峰时段能接受偶发 503
