# Team 任务成本对照

任务结束后，对 lead 的原生事件日志运行以下命令。成员日志应与 lead 日志位于同一目录。

```sh
python3 scripts/team-task-cost.py /path/to/sessions/LEAD.events
```

每条用户输入以「会话 ID#事件序号」标识。成员接到委派、lead 收到汇报时，读取方使用消息携带的发送回合追溯任务。多条用户输入共同占用的回合计入 `shared`，缺少来源的回合计入 `unattributed`。总量包含所有可读回合，各计一次，撤销对话也保留已经发生的消耗。只统计目录中仍有日志的会话；复制日志做对照时应一起保留成员文件。脚本拒绝含继承历史的分叉日志。

- `by_task` 汇总调用和 token；`by_session` 分列 lead 与各成员，`turns` 列出逐回合明细。调用计数覆盖 agent 循环交给模型适配器的请求，包括可观测的重试和收尾请求。适配器内部的 HTTP 重试、压缩等其他模型调用及供应商账单需要单独核对。
- `lead_wakeups` 统计以可追溯的成员消息启动的 lead 回合。正在进行的回合中途吸收汇报，不重复计为唤醒。
- `delegations` 和 `followups` 分别统计成功的 team delegate 和 tell。tell 包括普通补充说明，实际返工原因需结合任务判据分析。
- token 是收到的 usage 累计值。缓存输入单列，不要与输入再次相加。旧日志可能没有调用标记。结合缺少标记或 usage 的轮数、usage 记录数和缺少来源的消息数判断覆盖程度。同轮重试可能只有部分调用报告 usage。
- `stop_reasons_by_task` 是回合终止原因。任务是否完成需要独立判据，例如文件内容是否符合要求或审查是否找到了预设缺陷。

## 重跑三类任务对照

```sh
cargo nextest run -p atomcode-coding --test team --run-ignored only -E 'test(paired_role_budgets)' --success-output immediate
python3 scripts/tests/team-task-cost.py
```

两组使用相同脚本模型、文件、工具和验收条件，经实际 Team 调度、工具执行和事件格式统计。对照值 1 用来触发预算边界；成员还可发起收尾请求。每次模拟调用固定报告 100 个输入和 20 个输出 token，实验可重复验证调度成本，真实模型的上下文长度、完成率和计费仍需用真实任务衡量。

## 2026-11-22 真实模型对照

在两个新建的 TUI 会话中，用同一条提示委派一位 explorer 审查总账脚本及其测试。验收条件是解释为什么同轮两次调用、一次 usage 时，按轮统计的缺失数为 0，并给出能识别差额的指标。两次均交付了正确结论。第二次仅在临时配置中设置 explorer 请求预算为 1，另有一次纯文本收尾机会。

| explorer 预算 | 实际汇报方式 | 成员调用 | lead 委派回合调用 | lead 被唤醒后的调用 | 团队输入（其中缓存） | 团队输出 |
|---|---|---:|---:|---:|---:|---:|
| 未设置 | 主动 tell_parent | 3 | 2 | 2 | 144,590（114,432） | 6,128 |
| 1 | 预算耗尽后自动代报 | 2 | 2 | 3 | 168,246（156,672） | 5,713 |

两组各唤醒 lead 一次，均重新读取两份文件、停止成员并向用户交付审查结论。仅确认收悉和再次派工各为零。14 次调用均有 usage 记录。每组只运行一次，缓存命中量也不同，数据不足以估算生产成本或推荐默认预算。

### 显式要求成员附证据是否减少复读

在两个新的 TUI 会话中复用上述只读任务，均未配置角色预算。lead 和 explorer 的请求日志均记录模型为 `qwen4-max`。先跑显式证据组，再跑原提示组。用户提示的唯一差异是增加一句，让成员附文件、行号和支持每项结论的最短原文。两组均按同一标准验收：说明同轮两次调用、一次回执时该指标为 0，并给出检测差额的方法。

| 用户提示 | lead 复读文件数 | 团队调用 | 输入 token（其中缓存） | 输出 token | 验收 |
|---|---:|---:|---:|---:|---|
| 原提示 | 2 | 7 | 141,993（130,304） | 5,166 | 通过 |
| 显式要求附证据 | 2 | 8 | 181,088（166,400） | 7,805 | 通过 |

原提示组的 lead 已主动向成员索要行号和代码，所以本次比较只能回答「在用户提示里再加一次要求是否有帮助」。两组成员都给了证据，lead 均重新读取了相同的两份文件。显式要求组的成员对测试第 38 行有相互矛盾的描述；lead 指明这处矛盾并核实了原文。每组仅一次，调用和 token 差异不能单独归因于提示。后续可单独验证按疑点局部读取对成本和正确率的影响。

### 按疑点局部读取

用六个独立的 headless 会话固定成员汇报内容，仅测 lead 的核查阶段。每个会话使用 qwen4-max 和相同的两份源文件。三种汇报分别给出正确实现位置、将第 141 行误写为第 121 行、完全省略实现位置。每种各跑两次：对照提示要求核实并修正引用；局部读取提示额外要求先查相关行，必要时搜索和扩大范围。验收独立检查三项：返回实际指标值 0、确认或修复至第 141 行、说明如何识别本例缺少的那一次回执。独立运行总账读入一轮、一条请求头、两条调用标记和一条 usage，确认按轮指标为 0，调用数与回执数的差为 1。

| 汇报情况 | 源码行数（对照 / 局部） | 调用（对照 / 局部） | 对照答复 | 局部读取答复 |
|---|---:|---:|---|---|
| 引用准确 | 225 / 67 | 2 / 3 | 指标和引用正确，给出的按轮集合差无法发现缺少的那一次回执 | 三项通过，附带的负数成因解释有误 |
| 行号错误 | 225 / 68 | 3 / 3 | 三项通过 | 修正行号、算对指标，未说明按调用检测的办法 |
| 缺少实现引用 | 225 / 51 | 4 / 4 | 补对行号，将两次调用误作两条请求头，主结论答 1 | 补对行号、算对指标，未说明按调用检测的办法 |

源码行数只数 read_file 实际返回的带行号正文；搜索等工具的输出另计入工具结果字节。三项合计，对照 / 局部的工具结果为 47,058 / 19,276 字节，模型输入为 283,135 / 300,262 token（含缓存 241,152 / 247,040），输出为 21,866 / 13,223 token。对照的两次会话还调用了技能，其中一次执行了 Bash 验算。每格只有一次观察，工具选择、缓存命中与模型输出长度均可变化。当前样本支持按疑点缩小读取范围；没有足够证据将它设为默认省费策略。

### 交付前逐项回应原问题

沿用上一组局部读取实验的三份固定汇报、源码、模型和验收条件，每种新开一个 headless 会话。唯一增加的提示是 “Before handing off, answer each part of the user's original question explicitly, including any requested method the member report left unanswered.” 对照取上一轮局部读取组。判定依据是数值、实现引用和可用于发现本例回执缺口的方法均正确；只列出三个小标题不算通过。

| 成员汇报 | 原提示 → 增加交付提醒 | lead 模型调用 |
|---|---|---:|
| 引用准确 | 通过 → 通过 | 3 → 7 |
| 行号错误 | 漏答检测办法 → 修正行号并给出调用数减回执数 | 3 → 3 |
| 缺少实现引用 | 漏答检测办法 → 补对引用，但仍以按轮覆盖回答按调用缺口，未通过 | 4 → 4 |

逐项验收从 1/3 到 2/3；调用合计从 10 到 14，输入 token 从 300,262 到 453,596（其中缓存 247,040 → 405,248），输出从 13,223 到 24,673。四次额外调用均出现在引用准确的样本：lead 尝试运行测试，遇到临时副本缺少测试加载器所需的父目录脚本，随后改为重放事件。不能把这个差异归因于交付提醒本身。每种汇报仅一对观察，同一代码题也无法代表其他任务。本轮结果不支持将该提醒或额外审查回合设为 Team 默认。
