# TUI 全屏,流式形态由另一行承担

状态: 提案中

## 背景

TUI 有两种形态。**流式(inline)**:输出写进终端正常缓冲区,滚进原生 scrollback,
应用只控制底部若干行——原生滚动、搜索、复制都能用,退出后输出留在终端里。
**全屏(alternate screen)**:应用独占整块矩形,可以任意分屏,但要自己实现
滚动、搜索、复制,退出时屏幕被清掉。

不做决定会怎样:每个模块会各自假设一种,而分歧只在需要折叠一段旧内容、
或者需要把某个面板放到侧边时才暴露——那时已经写了很多代码。

## 决策

**全屏。** 应用持有整条流的渲染缓冲。

从需求推,不从现状推(现状 `atomcode-tuix` 是流式):

| 需求 | 推出什么 |
|---|---|
| 终态可以折叠、隐藏 | 折叠一个 turn、展开一条旧 reasoning → 整条流必须可寻址 |
| 模块可随意组合、变换 | 流区在流式下必然满宽置顶,面板放不到 transcript 侧边 |
| 自然语言调布局 | 一半请求得到「做不到」,这个入口的价值就塌了 |
| 折叠是默认呈现 | 用户随时要展开旧的;流式下滚过去就锁死 |

**流式形态不是被砍掉,它是另一行。** 日志形态的体验由 `ui-repl` 承担,
它已经存在。两种视图是**两行填同一个 `ui` 槽**,不是一个模式开关——
这正是这套架构自己的答案。

换来四条义务(每条都有执行者,见 `tui-composability.md` §四.7–10):
退出时回吐整条流、自己实现滚动、自己实现选择与复制、`Drop` 恢复终端(含 panic 路径)。

## 放弃了什么

**流式的三条真实优势:**

- **原生滚动 / 搜索 / 复制。** 全屏必须自己实现,而重新实现的版本通常更差
  (跨窗格选择、终端搜索、tmux copy-mode)。缓解:`/copy` `/save` 命令
  (tuix 已有,搬过来),但终端自带的搜索没有等价物。
- **退出后输出留在终端。** 对开发者工具是硬需求。**没有缓解,已接受**:曾经
  约定退出时把整条流回吐到正常缓冲区(义务 7),2026-09 取消——回吐的是与日志
  不同源的一份纯文本副本,只能事后补救,还会把工具给的转义序列带进人自己的
  缓冲区(`ESC[2J` 清掉它正要交还的那段滚动条,那里没有重绘 diff 兜底)。
  记录改由会话事件日志承担(`docs/adr/0024`,一条 `--continue` 就读回来),
  「滚上去看一眼」这个动作则确实没有了,记在
  [`docs/tui-composability.md`](../tui-composability.md) §九。
- **不劫持终端。** Ctrl-Z、嵌套 tmux、resize 的行为都更朴素。这条没有缓解,
  是接受的代价。

**「流式 + 全屏双模式」。** 曾经准备做:区域树同一个类型,流式下部分形状非法,
返回 `LayoutError::NotExpressibleInline`。放弃是因为它需要第三个 `Flushed` 块态
(呈现也冻结)、模式相关的布局合法性规则、两套 headless 记录(flush 字节流 +
live 网格),而这些复杂度换来的是一个已经由 `ui-repl` 覆盖的形态——**过度设计**。
代价:失去了「流式下也有面板」这种中间形态。

**「现状是流式,所以改全屏是功能倒退」这个论据本身。** 它是对现状的诉诸,
不是推导。记在这里是为了下次不要再用。

## 失效条件

- 若 `ui-repl` 被证明满足不了日志形态的需求(例如需要在流式下也有面板),
  「两行而非两模式」的结论需要重新论证。
- 若长会话的内存占用(全屏要留住整条流)成为实际问题,需要块的惰性化,
  且必须先给出「降级不改 `content_hash`」的判据。
- 若用户实测中「退出后看不见输出」和「不能用终端搜索」的痛感超过了
  分屏与折叠带来的收益,整个决策需要重估。这一条只能靠使用反馈,
  机器判不了。
