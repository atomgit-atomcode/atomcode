# 视图模块的行可以进入流的滚动尾部

状态: 提案中

## 背景

补 [ADR 0004](./0004-tui-stream-is-an-irreversible-block-sequence.md) 留下的一个口子。
0004 把屏幕分成两类:**流生产者**(追加不可逆块)与**视图模块**(每帧全量重画,无历史),
并规定「块属于流,不属于模块」。这条划清了不可逆性归谁,但没有回答第三件事:

**一个视图模块的行,能不能成为流的一部分,跟着流一起滚?**

现状是不能,而这带来两个后果:

1. `todo`(任务清单)与 `live`(这一轮在做什么)的矩形由布局树定死
   (`host::composer`),`moment.scroll` 对它们毫无影响 ——
   读者往回滚看历史时,面板钉在底部挡着历史。
2. `live` 为此开了一条特例:`showing()`(`modules/live.rs`)读
   `moment.scroll.is_at_bottom()` 决定自己存不存在。**一个视图模块为了决定
   自己画不画,去读宿主的滚动位置** —— 职责错位,而且 `todo` 没有这条,
   两个同类模块行为不一致。

`composer()` 的文档记下了当时为什么没做:
`LayoutOp::Show` 只有「对话之上」和「状态栏之下」两个方向,都在输入框的错误一侧,
所以面板只能把自己的位置写进树里 —— 而写进树就固定了矩形,也就与滚动无关。
`3050cb06` 的提交说明把这条约束写得更直白:「这一行的矩形是 composer 的,
一行把自己画进 stream 的滚动里就是画在自己矩形之外 —— 流的行数归宿主对着
offset 算」。**本条 ADR 就是拆掉这道几何约束。**

## 决策

**`El::Stream` 带一个 `tail` 声明:哪些模块的行构成流的尾部。**

```rust
El::Stream { tail: Vec<String> }
```

`tail` 里的模块**不再有自己的布局矩形**。它们的行是流内容的一部分:
参与滚动偏移,也参与滚动上界。`tail` 之外的一切照旧 ——
`El::place_into` 仍把 `Stream` 当一个叶子、交给它一个矩形,
`El::wanted` 仍让它报 1 行、靠 `grow` 吃满剩余。

**几何。** 设 pane 拿到 H 行,内容 = 块(B 行)+ 尾部(T 行):

```
visible_tail = (T - scroll).clamp(0, H)
block_scroll = (scroll - T).max(0)
scroll_limit = (B + T) - H
```

scroll 在 `[0, T]` 区间里 `block_scroll` 恒为 0 —— 尾部先被吃掉,块的**偏移**
不变。但这不是「块在屏幕上一动不动」:`block_rect.h` 每格长一行而内容底对齐,
所以块每格**下移一行**,顶上同时多露出一行更旧的。写判据时别把这两件事说成
一件:要断言的是「同几行字仍在视野里」,不是「块的行位置不变」。

尾部内部按「距底部的偏移」排,自底向上分配矩形。

**尾部总高要封顶,而且从最上面开始让。** 交给模块的是它**可见**的高度,于是
高于 pane 的模块会在若干个不同 offset 上都被问「你有 pane 这么高」,每次都排
出一模一样的画面 —— 读者滚 `T − H` 格,屏幕不动,只有「还有 N 行」在涨。所以
总高封在 `H − 1`(至少给对话留一行)。

**让行的顺序是自顶向下**:`tail` 里第一个先让完,才轮到下一个。贴着底边那个是
最新的、也是回答「是不是卡住了」的那一个;而它上方的东西多半有兜底(任务清单有
`window` 和 `+N 更多`),它没有。这一条曾经写反过 —— 注释说底边保留、循环却从
底边扣起,于是一份长计划在短终端里第一件事就是把 live 行清空。

**几何与 `stream_height` 必须用同一个封顶,也必须用同一个「pane 有多大」。**
两者都从 `Host::stream_room(size, moment) -> Rect` 出发:宽度是块被**量**的宽度
(不是屏幕宽度 —— `wide` 下对话区只占 65%),高度是尾部要分享的高度。这两个数
各自都有过一次"第二个答案",两次都表现为滚动的上界和画面对不上。

**每个 tail 模块保留自己的 part**,owner **就是模块 id**,不加前缀。
不并入流的缓冲区,理由是可验证性:每个模块仍是一个 `Placed`,
`Frame::containment_violations` 继续逐块检查「画的东西在自己
矩形内」。

id 而不加路径前缀,是因为一帧里 id 已经唯一:`named_twice` 拒绝一棵同时把某个
模块声明为 tail id 和独立叶子的树。加前缀的收益只是「帧里能看出层级」,代价是
`part("live")`/`part("todo")` 十几处调用点和 e2e 里按 rect 定位的用例全要改名 ——
而本条要的恰恰是「测试继续能按模块名定位」。

**尾部高度自适应,不刚性平移。** 交给模块的是它**可见**的高度,由模块自己
排版 —— 因为 `todo`(`modules/todo.rs` 的 `window`)与 `live`
(`modules/live.rs` 的 margin 判断)都已经会处理「行不够」:`todo` 会优先保住
正在做的那条(frontier)并用 `+N 更多`说明藏了什么,`live` 会在放不下 margin 时
丢掉 margin 保住文字。刚性平移**先切掉的正是这两样**。

**`stream_height` 收 moment 的引用,不收字段。** 尾部高度依赖 `Moment`(`live`
的高度由 `activity` 决定),而 `scroll_limit` 的契约是「调用方可能正持 moment
写锁」(`plugin.rs` 的两处确实如此),所以不能内部读锁。与 `stream_rows` 的签名
对齐。

**「量 → 改 → 重新读 → 量」。** 补偿必须量得到改动**之后**的世界,所以第二次
测量的 moment 要重新读,不能复用第一次的快照。这不只是整洁问题:折叠状态存在
`Presentation` 里而不是 `Moment` 里,用同一份快照回量两次会得到同一个数,`grew`
恒为 0 —— 点击展开一个块就什么都不会补偿。这是真实发生过的一次。

**四条路径,一个实现,一把锁。** 能改「有多少行可读」的有:折进一条事实
(`absorb`)、事件循环写 `activity`、两处取消、以及点击折叠一个块。它们在两个
线程上跑,所以除了共用一个方法,还要共用一个 gate:回合结束时事实和 activity
几乎同时到,各自量到同一个变化、各补一次,屏幕就跳两倍。

**「钉住阅读」必须符号对称,而且只有一个实现。** `absorb` 原来只在内容**变高**
时补偿滚动位置(`if grew > 0`),因为块只增不减。尾部进了滚动总量之后会缩
(activity 翻转、计划变短),缩的那一半不补偿会让读者正看的行往下跳。

更要紧的是**有几条路能改总量**,而它们不是一条路。尾部高度有一半来自
`Moment::activity`,那是由事件循环写的,**从不经过 `absorb`**;`state.turn`
那一半才走事实。先后顺序没有保证,所以只挂在 `absorb` 上的补偿会「有的回合
钉得住、有的钉不住」—— 比完全不钉更糟,因为它看起来是好的。

因此补偿是一个方法:`Host::pinned(only_when_held, change)` —— 「量、改、重新读、
再量、写」,外面套一把 gate。调用它的地方是 `absorb`(折一条事实)、
`Host::set_activity`、两处取消、以及点击折叠一个块(走 `held_while`)。哪条路
自己抄一份算术,就会在那里分叉;哪条路忘了,就只有它不钉。

`only_when_held` 是那个真实的差别:折一条事实时「在底部」的意思是跟随输出,不用
钉;而点击是一个人**指着**某一行,那一行必须留在原处 —— 展开一个块是向上长的,
最常见的发生地点恰好就是底部。

**「回到底部」徽标锚在对话区上,不是整个 pane。** 理由是**它不该盖住尾部**:
锚到 pane 会让它在 `0 < scroll ≤ T` 时压住尾部最后一行的右半截 —— 而尾部正是
往回滚的读者**没有**在看的东西,而滚轮一格一行,读者会经常停在这段区间。

(它的数字仍是 `moment.scroll`,含尾部那些行。在这个区间里对话其实没有行在
视野下方,所以数字说的不是「对话还有多少行」,而是「往上还有多少行内容」——
措辞按后者读。)

**`live` 的 `showing()` 不再读 `scroll`。** 滚动位置归宿主,模块只回答
「有没有话要说」(`doing()`)。这同时是上面 `stream_height` 契约的前提:
否则 `stream_height` 依赖 scroll、`scroll_limit` 又依赖 `stream_height`,成环。

**准入判据。** 进 `tail` 的是「关于这一轮正在做什么、值得被滚回去看的」内容
(`todo`、`live`);应用框架不进(`status`、`input`、`tip`)—— 尤其 `tip`,
它的不变量是「行常在、永不动输入框」(`modules::tip`)。
`tail` 是声明在树上的,所以 `/hide`、`[[remove]]`、`prune`
(`El::prune`)对它照常生效。

**一个 tail 成员可以让应用框架让位 —— 但只能由一个明确的判据驱动,且只在
让它让位的那一行自己身上。** 问题是按需出现的面板(`modules::ask`,见
[ADR 0010](./0010-every-panel-is-a-row.md)),出现时它要占的正是输入框那一块:
没有消息可打,要打的只有这一个答案。所以它出现时 `tip` 与 `input` 报 0 行,
输入框的整块高度回到对话。这条口子的形状很窄,值得写清它窄在哪:

- **判据是一个字段,不是一段逻辑。** `Moment::asking` 有值时才是「问题占着
  屏幕」,而它只在面板行已挂载时才被置上(`Host::sync_asking`)—— 摘掉
  `tui-panel-ask` 行后,问题退回流尾的纯文本兜底,输入框原地不动。所以
  「谁画问题」和「谁让位」永远是同一个答案,不会出现「为不存在的面板让了位」。
- **让位发生在仲裁处,不在模块里。** `asked_height`(`host.rs`)是唯一决定
  每个模块拿多少行的地方;`tip`/`input` 的 `height` 仍只回答「我自己需要几行」,
  与屏上有没有别的东西无关。反过来做(模块自己读 `asking` 后返回 0)会让一个
  模块的尺寸取决于兄弟模块,而 `Hug` 契约的全部意义就是避免这件事。
  唯一在 `height` 里读 `asking` 的是 `live` —— 因为它整个可见性本来就在
  `height`(由 `showing` 决定),再加一条「问题在场时让位」是同一个问题的第二
  个答案,不是跨模块耦合。
- **输入框不能为了「常在那」而不让位。** `tip` 的不变量是「行常在、永不动
  输入框」,而问题在时并没有手正伸向输入框 —— 这条让位不违背它的不变量,只是
  把它暂停在一个更弱的保证上。若日后有人给某个框架模块加「永不消失」的性质,
  这条要先被重新讨论。

**这不是「把 todo 塞进流」。** [`docs/tui-composability.md`](../tui-composability.md)
§一「Todo:同一批事实,两个模块」明确反对把 **todo 清单塞进流**:
清单做成块,每勾掉一项就追加一份,流被刷屏。那条结论不变,本条也不与它冲突 ——
两件事的区别是:

| | 做成块(被否) | 排在滚动尾部(本条) |
|---|---|---|
| 模块类型 | 流生产者 | **仍是视图模块** |
| 每次变更 | 追加一个不可逆块 | 每帧重画,不追加任何东西 |
| 有历史 | 有(流被刷屏) | **无**(与今天一致) |
| 变了什么 | 流的内容 | 只是**行画在哪** —— 从固定矩形改为滚动序列的尾部 |

换句话说:本条只挪动「面板的行在哪」,不改变「面板是不是每帧重画、有没有历史」。
`content_hash`、`Live → Settled`、不可逆性一律不受影响,§四第 8 条
(「滚动位置在 `Moment` 里,且不影响任何块的 `content_hash`」)继续成立。

**实施分两步:`todo` 先,`live` 后。** 两者的收益不对称 —— `todo` 可能有 5–10 行,
能被**部分**滚出视野;`live` 只有 2 行,往回滚 2 行就出视野,与现状的「让位」
观感几乎相同。先做 `todo` 可以在较小的影响面上验证最危险的部分
(`stream_height` 的签名、pin 的符号性、尾部几何),而 `live` 那条 `showing`
判据此时还能当对照组。

## 放弃了什么

**让位(现状):读者一往回滚,面板整体消失。** 零成本,`live` 已经在这么做,
`todo` 加三行即可。放弃有两个理由:一是它是二值跳变 —— 一个 10 行的 `todo`
面板只滚 1 行就整块消失,而「滚上去扫一眼再回来」是常见动作;二是它要求模块
读宿主的滚动位置,与 0004 划的职责不符。代价:改动跨布局引擎与滚动算术。

**刚性平移:按全高渲染,再切掉滚出去的几行。** 更接近「整块移动」的字面语义,
而且完全可见时输出与自适应方案**逐行相同**。放弃是因为切的顺序与两个模块的
排版策略相反:`live` 的行序是 `[空白, 文字]`(margin 在**上**),底部先滚掉的
是**文字**,会留一行空白;`todo::window` 的策略是「默认取尾部、按 frontier
往前拉」,从底部切**正好切掉它刚优先保留的 frontier**。

**并入流的单一缓冲区(帧里只有 `part("stream")`)。** 一套裁剪逻辑,
帧里更干净。放弃是因为它会丢掉每个模块的帧内身份:containment 检查、
`part("live")` 式的测试定位、以及将来某一行要被单独寻址(点击、高亮)
都会变难。代价是每个 tail 模块各算一次可见区间。

**给 tail 模块各自一个固定矩形,由宿主平移。** 保住模块身份,改动更小。
放弃是因为「部分滚出」要么回到刚性切行(行为错,同上),要么给每个模块引入
裁剪概念 —— 后者等于把滚动语义复制进每个模块。

## 失效条件

- 若出现**在尾部需要交互**的模块(点击折叠、按行选中),「它是一串行」的模型
  不够,要回到「每个模块自己的矩形 + 裁剪」。
- 若尾部高度变化的频率高到 pin 的补偿在观感上仍然抖,「尾部属于滚动内容」
  需要重新权衡(一条出路是给尾部一个固定预留高度)。
- 若出现第三类需要「有历史、又要每帧重画、又要可滚」的模块,
  0004 的两类划分与本条要一起重新论证。
