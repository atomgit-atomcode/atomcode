# 视图模块的行可以进入流的滚动尾部

状态: 提案中

## 背景

补 [ADR 0004](./0004-tui-stream-is-an-irreversible-block-sequence.md) 留下的一个口子。
0004 把屏幕分成两类:**流生产者**(追加不可逆块)与**视图模块**(每帧全量重画,无历史),
并规定「块属于流,不属于模块」。这条划清了不可逆性归谁,但没有回答第三件事:

**一个视图模块的行,能不能成为流的一部分,跟着流一起滚?**

现状是不能,而这带来两个后果:

1. `todo`(任务清单)与 `live`(这一轮在做什么)的矩形由布局树定死
   (`host::composer`,`host.rs:1497`),`moment.scroll` 对它们毫无影响 ——
   读者往回滚看历史时,面板钉在底部挡着历史。
2. `live` 为此开了一条特例:`showing()`(`modules/live.rs`)读
   `moment.scroll.is_at_bottom()` 决定自己存不存在。**一个视图模块为了决定
   自己画不画,去读宿主的滚动位置** —— 职责错位,而且 `todo` 没有这条,
   两个同类模块行为不一致。

`composer()` 的文档(`host.rs:1479-1483`)记下了当时为什么没做:
`LayoutOp::Show` 只有「对话之上」和「状态栏之下」两个方向,都在输入框的错误一侧,
所以面板只能把自己的位置写进树里 —— 而写进树就固定了矩形,也就与滚动无关。
`3050cb06` 的提交说明把这条约束写得更直白:「这一行的矩形是 composer 的,
一行把自己画进 stream 的滚动里就是画在自己矩形之外 —— 流的行数归宿主对着
offset 算」。**本条 ADR 就是拆掉这道几何约束。**

## 决策

**`El::Stream` 带一个 `tail` 声明:哪些模块的行构成流的尾部。**

```rust
El::Stream { tail: Vec<String> }
```

`tail` 里的模块**不再有自己的布局矩形**。它们的行是流内容的一部分:
参与滚动偏移,也参与滚动上界。`tail` 之外的一切照旧 ——
`place_into`(`el.rs:401`)仍把 `Stream` 当一个叶子、交给它一个矩形,
`wanted`(`el.rs:505`)仍让它报 1 行、靠 `grow` 吃满剩余。

**几何。** 设 pane 拿到 H 行,内容 = 块(B 行)+ 尾部(T 行):

```
visible_tail = (T - scroll).clamp(0, H)
block_scroll = (scroll - T).max(0)
scroll_limit = (B + T) - H
```

scroll 的前 T 行由尾部自己吃掉,块纹丝不动;超出之后块才开始滚。
尾部内部按「距底部的偏移」排,自底向上分配矩形。

**每个 tail 模块保留自己的 part**,owner 写作 `stream.tail.<id>`。
不并入流的缓冲区,理由是可验证性:每个模块仍是一个 `Placed`,
`Frame::containment_violations`(`frame.rs:458`)继续逐块检查「画的东西在自己
矩形内」,测试也继续能按模块名定位。`Frame::part`(`frame.rs:357`)是精确
字符串匹配,所以名字写全,查找函数不变聪明(不做后缀匹配 —— 那会引入歧义)。

**尾部高度自适应,不刚性平移。** 交给模块的是它**可见**的高度,由模块自己
排版 —— 因为 `todo`(`modules/todo.rs` 的 `window`)与 `live`
(`modules/live.rs` 的 margin 判断)都已经会处理「行不够」:`todo` 会优先保住
正在做的那条(frontier)并用 `+N 更多`说明藏了什么,`live` 会在放不下 margin 时
丢掉 margin 保住文字。刚性平移**先切掉的正是这两样**。

**`stream_height` 收 `&Moment`。** 尾部高度依赖 `Moment`(`live` 的高度由
`activity` 决定),而 `scroll_limit` 的契约是「调用方可能正持 moment 写锁」
(`host.rs:1329-1330`;`plugin.rs:876/915` 确实如此),所以不能内部读锁。
与 `stream_rows` 的签名对齐(`host.rs:1315`)。

**「钉住阅读」必须符号对称。** `absorb` 现在只在内容**变高**时补偿滚动位置
(`host.rs:761-767` 的 `if grew > 0`),因为块只增不减。尾部进了滚动总量之后
会缩(activity 翻转、计划变短),缩的那一半不补偿会让读者正看的行往下跳。

**`live` 的 `showing()` 不再读 `scroll`。** 滚动位置归宿主,模块只回答
「有没有话要说」(`doing()`)。这同时是上面 `stream_height` 契约的前提:
否则 `stream_height` 依赖 scroll、`scroll_limit` 又依赖 `stream_height`,成环。

**准入判据。** 进 `tail` 的是「关于这一轮正在做什么、值得被滚回去看的」内容
(`todo`、`live`);应用框架不进(`status`、`input`、`tip`)—— 尤其 `tip`,
它的不变量是「行常在、永不动输入框」(`modules/tip.rs:10-22`)。
`tail` 是声明在树上的,所以 `/hide`、`[[remove]]`、`prune`
(`el.rs:334`)对它照常生效。

**这不是「把 todo 塞进流」。** [`docs/tui-composability.md`](../tui-composability.md)
§一「Todo:同一批事实,两个模块」明确反对把 **todo 清单塞进流**:
清单做成块,每勾掉一项就追加一份,流被刷屏。那条结论不变,本条也不与它冲突 ——
两件事的区别是:

| | 做成块(被否) | 排在滚动尾部(本条) |
|---|---|---|
| 模块类型 | 流生产者 | **仍是视图模块** |
| 每次变更 | 追加一个不可逆块 | 每帧重画,不追加任何东西 |
| 有历史 | 有(流被刷屏) | **无**(与今天一致) |
| 变了什么 | 流的内容 | 只是**行画在哪** —— 从固定矩形改为滚动序列的尾部 |

换句话说:本条只挪动「面板的行在哪」,不改变「面板是不是每帧重画、有没有历史」。
`content_hash`、`Live → Settled`、不可逆性一律不受影响,§四第 8 条
(「滚动位置在 `Moment` 里,且不影响任何块的 `content_hash`」)继续成立。

**实施分两步:`todo` 先,`live` 后。** 两者的收益不对称 —— `todo` 可能有 5–10 行,
能被**部分**滚出视野;`live` 只有 2 行,往回滚 2 行就出视野,与现状的「让位」
观感几乎相同。先做 `todo` 可以在较小的影响面上验证最危险的部分
(`stream_height` 的签名、pin 的符号性、尾部几何),而 `live` 那条 `showing`
判据此时还能当对照组。

## 放弃了什么

**让位(现状):读者一往回滚,面板整体消失。** 零成本,`live` 已经在这么做,
`todo` 加三行即可。放弃有两个理由:一是它是二值跳变 —— 一个 10 行的 `todo`
面板只滚 1 行就整块消失,而「滚上去扫一眼再回来」是常见动作;二是它要求模块
读宿主的滚动位置,与 0004 划的职责不符。代价:改动跨布局引擎与滚动算术。

**刚性平移:按全高渲染,再切掉滚出去的几行。** 更接近「整块移动」的字面语义,
而且完全可见时输出与自适应方案**逐行相同**。放弃是因为切的顺序与两个模块的
排版策略相反:`live` 的行序是 `[空白, 文字]`(margin 在**上**),底部先滚掉的
是**文字**,会留一行空白;`todo::window` 的策略是「默认取尾部、按 frontier
往前拉」,从底部切**正好切掉它刚优先保留的 frontier**。

**并入流的单一缓冲区(帧里只有 `part("stream")`)。** 一套裁剪逻辑,
帧里更干净。放弃是因为它会丢掉每个模块的帧内身份:containment 检查、
`part("live")` 式的测试定位、以及将来某一行要被单独寻址(点击、高亮)
都会变难。代价是每个 tail 模块各算一次可见区间。

**给 tail 模块各自一个固定矩形,由宿主平移。** 保住模块身份,改动更小。
放弃是因为「部分滚出」要么回到刚性切行(行为错,同上),要么给每个模块引入
裁剪概念 —— 后者等于把滚动语义复制进每个模块。

## 失效条件

- 若出现**在尾部需要交互**的模块(点击折叠、按行选中),「它是一串行」的模型
  不够,要回到「每个模块自己的矩形 + 裁剪」。
- 若尾部高度变化的频率高到 pin 的补偿在观感上仍然抖,「尾部属于滚动内容」
  需要重新权衡(一条出路是给尾部一个固定预留高度)。
- 若出现第三类需要「有历史、又要每帧重画、又要可滚」的模块,
  0004 的两类划分与本条要一起重新论证。
