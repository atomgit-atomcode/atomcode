# Download permission needs a publication boundary

Status: decision accepted; event-cancellation-only implementation rejected before release. Full per-origin transfers/CDP remain unfinished.

Baseline release/v5.2.7 c86fb5425, clean main and isolated worktree. Local Codex remains 806d9732c9; config/src/browser_use.rs defines independent origin permissions but provides no executor here. CodingRuntime remains the sole agent owner; the optional backend owns its Chrome context, proxy and artifacts. No runtime/session protocol change is needed to investigate this execution boundary.

The pinned Playwright MCP automatically calls download.saveAs. A preliminary public download-event guard cancels denied final origins before the upstream listener and initially looks sufficient: one allowed payload persists and seven denied/redirect samples do not. It is not sufficient. In an actual isolated Chrome/MCP test, delaying event handling by one second lets Chrome finish its tiny download; cancel then resolves successfully but the upstream SDK still saves the denied payload. Pinned coreBundle.js Artifact._cancel delegates to the browser cancellation callback without invalidating an already completed artifact; Artifact.saveAs accepts finished artifacts. API success is not proof that a completed result cannot be saved.

The first HTTP experiment never reached this seam because the existing proxy already rejects attachment responses. HTTPS fixtures use only an ephemeral certificate's SPKI pin to isolate the artifact seam while retaining the origin proxy. The delayed test models scheduling latency, not an estimate of normal occurrence frequency. It preserves the denied saved bytes and cancellation event as independent evidence.

Keep production version 1 unchanged: acceptDownloads=false, HTTP attachment refusal and direct upload/code/CDP denials. Withdraw the unshipped version-2 parser/proxy/event-guard draft; do not advertise an enforcement capability that the completed-download case disproves. Preserve the draft only as private experimental evidence, not a supported backend. A successful happy-path sample or additional cancellation retries cannot fix the publication race. Modifying SDK private download handlers, deleting a published file afterward, or allowing all downloads and relying on cleanup is not selected.

The transfer implementation must own the publication seam. Next implementation should keep implicit browser download persistence disabled and add a controlled explicit artifact-transfer path, validating trusted exact-origin permission at every redirect and writing only generated files beneath the owned artifact root after validation. Blob/opaque origins, authenticated context, upload file capabilities, cancellation/unknown effects and target-scoped CDP must be designed and tested rather than inferred. If the external backend cannot expose such a seam safely, replace that execution adapter instead of weakening or silently ignoring permissions. Full allow/deny access/upload/download/CDP and managed CLI/TUI configuration remain the original goal; this decision does not redefine it as fixed-denial compatibility.

The opt-in source-only characterization verifier records both ordinary and delayed behavior through actual MCP/Chrome, plus versions/source hashes and cleanup. It intentionally runs the rejected acceptDownloads=true setup only inside synthetic loopback fixtures and is never a production backend option. No dependencies, bundled browser/native binary, credential, provider, row configuration or OS grant changes are introduced.
