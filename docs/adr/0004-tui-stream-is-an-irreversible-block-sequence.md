# TUI 的流是不可逆块序列,不是日志的纯投影

状态: 提案中

## 背景

把 TUI 拆成插件后,需要先定下「屏幕上的内容随时间怎么变」。
不定下来,每个模块会各自假设一套,而分歧只在两个模块同屏时才暴露。

终端的性质给了约束:用户看到的流不可逆。它有**运行态**和**终态**——
运行态可以变,终态不能变,但可以折叠、隐藏,且只能顺序增加。

## 决策

屏幕内容是**块序列**,每块单向走完 `Live ──settle──> Settled`,没有返回边。

不可逆由**借用检查器**执行,不靠约定:`Stream` 刻意不提供任何能拿到
`&mut settled[i]` 的东西;生产者只拿到 `StreamWriter`,它只暴露
`open` / `amend`(只借得到 live) / `settle`。

「不能变」与「可以折叠」的和解是把两件事分开:**内容**在 settle 后冻结
(量具是 `content_hash` 恒定),**呈现**(折叠/隐藏/折行宽度)仍可变。
`Presentation` 存在宿主里、按 `BlockId` 索引,不在块里——所以
「折叠不改内容」是结构性的,不是纪律性的。

块的下标顺序是**发出顺序**;状态可以乱序从 Live 变 Settled
(并行工具调用同时有 N 个未决,三号槽可以比五号槽晚结算)。

块属于**流**,不属于模块。卸载生产者只停止新块,不追回旧块。

由此强制分出两类模块:**流生产者**(追加块,不可逆,有历史)与
**视图模块**(每帧全量重画,无历史)。

## 放弃了什么

**「屏幕是日志的纯投影,每帧从状态重算」。** 这是本设计的第一版,更简洁,
而且和 `derive_messages`、持久化构成漂亮的「一份日志三个投影」。
放弃它是因为**重算允许改写终态**:同一段已经落定的输出,下一帧可以变成
别的样子。代价是失去了那个对称性,以及必须显式管理块的生命周期。

**`Stream { live: Option<Block> }`(单个运行态块)。** 更简单,不变量更强。
放弃是因为并行工具调用同时有 N 个未决,这个形状表达不了。
代价是 `Slot` 多一个变体,越界断言多一条。

**统一的 `Panel` 抽象(不分两类)。** 少一个概念。放弃是因为不可逆只适用于
流生产者;混同会长出两类错误——「状态栏也想追加历史」和「transcript 被整体重画」。
代价是新增模块时要先想清楚自己属于哪类。

**让流生产者直接处理按键(用于 `Choice` 块)。** 最直接。放弃是因为流就不纯了,
`render` 的无副作用义务破。改走 `user-questions` 缝:TUI 的提供方就是 `Choice`
块的生产者。代价是多一跳间接。

## 失效条件

- 若出现第三类模块(既有历史又需每帧重画),两类划分需要重新论证。
- 若 `content_hash` 被证明不足以表达冻结性(例如内容含不可哈希的外部引用),
  量具需要更换,而整套判据依赖它。
- 若终端与渲染成本变化到「每帧重算整条流」不再昂贵,纯投影方案的简洁性
  可能重新占优——但它仍然解决不了终态被改写的问题,所以这条失效条件
  只影响性能论据,不影响正确性论据。
