# 布局是入日志的运行时状态,三条入口收敛到一个 op 词汇表

状态: 提案中

## 背景

布局要能在运行时调整,且有三种入口:快捷键、菜单命令、自然语言(模型感知后调整)。
不做决定会怎样:三条入口各写一份布局编辑实现,然后慢慢分叉——
快捷键能做的命令做不了,模型描述的和实际渲染的说两样。

同时,「屏幕可见即已记录」要求屏幕上有什么必须能从日志重建。
布局决定屏幕上有什么。

## 决策

**布局是状态,由配置初始化。** 变更是 `LayoutOp`(Split / Close / Swap / Resize /
Show / Hide / Focus / Preset / Undo),不是整棵树替换——op 可以被校验、撤销、
记录、描述。

**三条入口只是翻译器,落点是同一个 `apply(op) -> Result<(), LayoutError>`。**
配一条防分叉闸门:同一个意图分别走键位 / 命令 / 工具,产出的 op 必须相等。

**模型那条不新建机制。** 感知 = 布局行往 `PromptRegistry` 贡献一个片段
(每次请求现读,所以永不漂移);动作 = 往 `ToolsSvc` 注册 `adjust_layout` 工具
(风险 `Safe`,可 Undo,不走审批)。两者由同一行提供、从同一份状态导出,
所以描述与渲染不可能说两样。

**变更入会话日志**:`SessionEvent::LayoutChanged { op }`,
`is_model_visible() == false`(与 `Notice` 同类:给屏幕看的事实,不给模型看)。

失败必须带模型能用的原因(`NoSuchModule` 列出可用模块名等),
不许 panic,不许静默无效。

## 放弃了什么

**布局作为挂载期配置(不可运行时改)。** 最简单,而且和其它行一致。
放弃是因为需求明确要求运行时可调。代价:布局成了状态,多一处需要持久化与恢复。

**整棵树替换而非 op。** 接口更小(`set_layout(tree)`)。放弃有三个理由:
无法表达 Undo(要另建撤销栈)、无法给出可执行的失败原因(只能说「这棵树非法」)、
模型要输出整棵树而不是一个意图——出错率高得多。
代价:op 的集合是封闭的,新的布局操作要加变体。

**布局变更不入日志(存在单独的偏好文件或内存里)。** 日志更干净。
放弃是因为恢复会话时屏幕会和之前不一样——**时间可组合性破了**。
入日志还白送三件事:Undo = 重放到第 N 条(不需要撤销栈)、
场景构造器能构造任意布局状态、连续 `Resize` 由 fold 合并。
代价:日志里多一类非模型可见的事实。

**给模型另建一套布局描述通道(而不是复用 `PromptRegistry` / `ToolsSvc`)。**
可以做得更精确。放弃是因为那会是第二个家,与渲染用的状态必然分叉。

## 失效条件

- 若 `LayoutOp` 的变体数量增长到难以让模型可靠选择,
  「一个封闭 op 集合」需要重新评估(可能要退回受限的树描述)。
- 若布局变更的频率高到污染日志(fold 合并不足以吸收),
  「入日志」需要重新权衡。
- 若出现需要跨会话共享/同步布局的需求,会话日志不是正确的家。
